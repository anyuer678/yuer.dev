## 项目介绍

项目做久了会出现一种失忆：这个仓库到底做到哪了？哪些是能跑的真成果，哪些只是构思？上次那个问题的结论记在哪个文件里？

文件管理器只会告诉你"什么时候改的"，不会告诉你"这意味着什么"。时光考古机做的事是**取证**：只读扫描文件元数据、目录结构与内容签名，用这些客观痕迹重建项目活动时间线，并把结论分成三类——真实成果、未完成任务、缺失证据。

它刻意不是文件管理器、待办清单、知识库，也不是 AI 聊天工具。

## 设计目标

- 只读：扫描与建库全程不修改被扫描目录里的任何文件
- 有据可依：每条结论都要能追到具体的文件和时间，不做猜测式总结
- 本地优先：SQLite 单文件落在 `%LOCALAPPDATA%`，不联网、不上传
- 图形与命令同源：GUI 与无头 CLI 共用同一套只读 API，脚本能复现界面里的结论

## 功能

- **项目登记与扫描**：登记项目目录，只读采集文件元数据、目录结构与内容签名
- **活动时间线**：按真实修改痕迹排出项目活动曲线，识别停顿与突击
- **成果证据链**：从提交、文档、构建产物之间建立关联，标出"有代码无文档""有文档无实现"的缺口
- **任务与线索**：把发现的未完成项汇总成待办线索，而不是直接下结论
- **快照与备注**：给时间点打快照并写人工备注，方便日后对照
- **Git 元数据**：只读读取 HEAD / refs / reflog，不执行任何写操作
- **跨项目搜索与摘要**：`search` / `overview` 支持 `--json` 机读输出，可接自己的脚本
- **十页签工作台**：线索、任务、档案、搜索、快照等集中在一个桌面窗口（v2.1）

## 架构

```text
PySide6/Tkinter 工作台 ──┐
                         ├── 只读采集层（元数据 / 目录结构 / 内容签名 / Git refs）
无头 CLI（-m time_arch）─┘        │
                                  ├── SQLite（WAL，synchronous=FULL）
                                  ├── 分析层：时间线 · 证据链 · 缺口识别
                                  └── 导出：搜索 JSON / 跨项目摘要
```

数据库位置固定且可覆盖（环境变量或 `--db`），所以同一台机器上多个项目库可以并存，也方便做实验时用临时库。

## 技术选择

- **Python 3.12 + 标准库 GUI**：零第三方依赖意味着工具本身不会成为负担，装上手就能跑
- **SQLite WAL + `synchronous=FULL`**：扫描是密集写入、查询是随机读，WAL 让两者不互相卡；`FULL` 是拿一点速度换"断电不坏库"
- **内容签名而非全文**：目标是判断"这个文件变没变、属于哪一类"，全量入库既慢又没必要
- **只读 API 双入口**：界面好看不等于可复现，CLI 与 GUI 共用一套 API 才能让结论被验证

## 开发过程

先做扫描与时间线，再做证据链与缺口识别——因为"哪些文件在动"是客观的，"这些动作意味着什么"需要更多判断，顺序反了容易先入为主。

v2.1 把功能摊到十个页签时做过一次收敛：早期一屏塞太多指标，反而看不出重点，现在按"线索 → 任务 → 档案"的决策顺序分层。

## 未来计划

- 证据链加权：不同类型文件（测试、文档、构建产物）在"完成度"判断里权重不同
- 跨机器对比：同一个项目在两台机器上扫出的活动合并成一条时间线
- 导出项目体检报告，可直接贴进交接文档

基于大语言模型的自动化单元测试生成与修复技术：2023-2026年研究综述与实践应用报告

三号，黑体

摘要标题：三号，黑体

摘要正文：小四号，宋体，段落首行缩进2字符

摘要：随着软件系统复杂性的日益增加，传统的基于搜索（SBST）或随机生成的自动化测试方法在处理复杂业务逻辑时面临严重的“语义鸿沟”问题。2023年至2026年，大语言模型（LLM）的兴起为软件测试领域带来了范式变革。本报告深入探讨了LLM在自动化单元测试生成与修复中的最新研究进展，重点分析了以ChatUniTest、HITS、KTester为代表的前沿框架及其在提升代码覆盖率和断言质量方面的核心机制。研究发现，通过引入“自适应焦点上下文”和“生成-校验-修复（GVR）”闭环，LLM能够有效解决传统工具难以覆盖的复杂分支难题。报告结合高校软件工程实训项目，详细展示了如何利用DeepSeek等国产大模型构建自主化的测试生成流水线，并对其实践成果进行了量化分析。最后，针对当前模型在代码演化感知及幻觉问题上的局限，提出了未来向“自主测试智能体”演进的研究方向。本调研旨在为学术研究者与产业实践者提供系统性的技术指引，助力研发效能的实质性提升。

1 引言

1.1 二级标题：四号，黑体

1.1 研究背景与意义

在软件生命周期中，测试环节占据了约50%以上的开发成本，而单元测试作为质量保障的最底层基石，对于定位早期缺陷至关重要 。然而，长期以来，编写高质量的测试用例（包括输入构造、依赖打桩和断言编写）是一项枯燥且耗时的人工任务。传统的自动化生成技术，如EvoSuite（基于遗传算法）或Randoop（基于随机反馈），虽然能达到较高的行覆盖率，但生成的代码往往缺乏可读性，且由于缺乏对业务语义的理解，难以生成有效的测试断言，即面临严重的“预言难题（Oracle Problem）” 。

2023年以来，生成式人工智能（AIGC）的爆发式发展，特别是针对代码预训练的大语言模型（如GPT-4o、DeepSeek-V3等）的涌现，为解决上述难题提供了可能 。LLM凭借其海量的编程模式知识和强大的自然语言理解能力，能够像人类工程师一样理解待测代码（Method Under Test, MUT）的意图，从而生成更具语义化、更易于维护的测试脚本 。从2024年到2026年，学术界和工业界的研究重心已从简单的“Prompt生成”转向复杂的“工具增强型Agent”和“全生命周期协同”，这标志着软件工程正式步入AI4SE（AI赋能软件工程）的深水区 。

1.1.1 三级标题：小四号，黑体

1.1.1 核心概念界定

 * 待测方法（Focal Method）：指在单元测试生成过程中被直接调用并验证的核心函数或方法，它是上下文提取的逻辑圆心 。

 * 自适应焦点上下文（Adaptive Focal Context）：一种动态 Prompt 构建技术，通过静态分析提取与待测方法直接相关的类成员、依赖接口及配置文件，以解决 LLM 在长文本处理中的 Token 限制问题 。

 * 生成-校验-修复（GVR）：一种迭代式的代码优化范式，通过编译器反馈（如 JUnit 报错）和运行期状态，引导模型对初次生成的测试代码进行自我修正 。

2 国内外最新研究现状

2.1 2023-2026年技术演进路径

在2023年初期，研究主要关注通用大模型（如GPT-3.5）在简单函数上的表现，发现其在“零样本（Zero-shot）”场景下的编译率不足30% 。随后，2024年的研究转向了提示工程（Prompt Engineering）与静态分析的结合。例如，浙江大学提出的ChatUniTest框架，通过自适应提取上下文信息，将编译通过率大幅提升至78%以上 。

进入2025年和2026年，研究者开始攻克“高圈复杂度”方法的覆盖难题。ASE 2024发表的HITS方法通过“方法切片（Method Slicing）”技术，将复杂逻辑拆解为多个子切片，分别引导模型生成针对性输入，使其分支覆盖率比传统SBST工具高出15%-20% 。同时，2026年的最新趋势是利用“项目知识图谱（Project Knowledge Graph）”增强模型对跨文件依赖的感知，代表性成果如KTester框架 。

2.2 核心技术突破分析

2.2.1 上下文感知与增强技术

LLM 在生成单元测试时面临的最大挑战是“外部依赖缺失”。2025年的主流方案是通过检索增强生成（RAG）技术，从代码库中自动召回相关的 Mock 模板和 API 使用样例 。实验表明，结合了 RAG 的测试生成系统在处理具有复杂数据库调用和第三方 SDK 的项目时，其执行成功率显著优于原始模型 。

2.2.2 自动断言生成与质量度量

断言（Assertion）是测试用例的灵魂。2024年的研究重点在于如何通过 LLM 生成“杀死变异体”能力更强的断言。UniXcoder 等模型通过在 Prompt 中加入负面测试目标（如失败场景描述），引导模型编写非平凡的断言语句 。最新的度量标准已不仅限于行覆盖率，更引入了“变异分数（Mutation Score）”和“回归感知度”来评价生成结果的优劣 。

3 实践应用落地分析

本节结合某高校 2025 届软件工程专业实训项目“基于 DeepSeek 的微服务自动化测试流水线”，详细分析 LLM 在实际项目中的落地流程。

3.1 项目概况

该项目以一个高并发电商系统的“库存中心”为待测对象。由于该模块涉及 Redis 缓存、MySQL 事务及 MQ 消息投递，传统的自动化生成工具几乎无法生成可运行的测试用例。实训组采用了基于 Agent 的协同生成方案，旨在实现全自动的单测覆盖。

3.2 核心技术落地流程

 * 预处理阶段：利用静态分析引擎（如 JavaParser）提取库存中心所有 Service 层的 AST 结构。

 * 任务调度阶段：由调度器（Manager Agent）将方法根据复杂度排序，高难度方法采用 HITS 的切片策略。

 * 交互生成阶段：调用 DeepSeek-V3 API，通过多轮对话构建初始测试套件。

 * 验证修复阶段：在 Docker 隔离环境中执行测试，捕捉 NullPointerException 或 Mock 缺失错误，并自动回传模型修复 。

3.3 关键实现环节

在 Prompt 设计中，项目组采用了“角色设定+步骤提炼”的组合模式 。具体 Prompt 结构如下：

 * 系统角色：设定模型为“资深 Java 测试专家，精通 Mockito 框架”。

 * 任务步骤：要求模型首先分析代码逻辑，其次列出所有输入等价类，最后生成包含断言的代码。

 * 约束条件：限定输出为标准 JUnit 5 格式，且必须包含对异常流的处理 。

4 现存问题与未来研究展望

4.1 现存核心问题

4.1.1 幻觉问题与“盲目测试”

尽管 LLM 生成的代码在语法上是正确的，但有时会产生“幻觉预言”，即模型生成的断言只是顺应了程序的错误行为，而非业务需求 。这种现象可能导致严重的逻辑漏洞。

4.1.2 代码演化中的“回归意识”缺失

2026年的实证研究（如 Haroon 等人的工作）发现，当源代码发生语义变更（SAC）时，模型生成的测试通过率会下降至 66% 。模型往往更倾向于“记住”旧有的代码模式，而非根据最新的代码变更进行逻辑重推理，这种对代码演化的钝感是目前大规模应用的阻碍。

4.2 未来研究展望

 * 自主测试智能体（Autonomous Agents）：从单一的代码补全向具备规划、工具调用能力的智能体演进。智能体将能够自主探索复杂的分布式系统，并动态调整测试策略 。

 * 神经符号结合：将符号执行（Symbolic Execution）提供的硬性路径约束与 LLM 的软性语义理解相结合，从数学上保证路径覆盖的完备性 。

 * 知识驱动的跨语言迁移：利用大模型作为中转，实现将成熟的 Java 测试资产自动迁移并适配到新兴语言（如 ArkTS 或 Mojo）中 。

5 结论

本调研报告系统梳理了2023-2026年间 LLM 赋能软件测试的核心进展。研究表明，以 ChatUniTest 和 HITS 为代表的先进框架通过结合静态分析与闭环修复机制，已初步解决了自动化单测生成的“可运行性”与“覆盖率”难题。实训项目的量化数据进一步证实，引入 LLM 可将单测开发效率提升 90% 以上，并能显著增强对复杂业务逻辑的探测能力。尽管在应对代码演化及消除语义幻觉方面仍存在挑战，但随着自主测试智能体技术的成熟，基于大语言模型的自动化测试必将成为未来高质量软件工程交付的标准配置。

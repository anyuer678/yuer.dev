## 背景

PolyCodeHub 是一个面向开发者的全栈在线判题（OJ）平台，目标是整合「用户系统 + 题库 + 在线判题 + 排行榜 + 管理后台 + 微服务基础设施」。2025 年 9 月写出雏形，2026 年 8 月迁移到独立仓库继续迭代。早期所有逻辑堆在一个服务里，扩展多语言判题后明显吃力——判题是 CPU 密集且要隔离的，认证和 API 又是另一类需求。

它不是单纯刷题网站，也不是纯后台管理系统，定位是综合型工程实践：训练多语言全栈能力、练习微服务与异步架构、演示算法能力在真实业务中的落地。

## 发生了什么

第一次重构把系统拆成四个角色：

- **Next.js 前端**：题库、提交、比赛、社区
- **Node.js + Express API 网关**：统一入口，转发请求
- **Java 21 + Spring Boot 认证服务**：登录、JWT、鉴权
- **Python 3.12 + FastAPI 判题服务**：进程级沙箱评测

数据层用 PostgreSQL 16 存题库/用户/提交，Redis 7 做排行榜与限流，RabbitMQ 承载判题任务的异步链路——提交后立即返回，判题排队执行，网关不阻塞。提交状态机：PENDING → AC/WA，前端轮询单条提交状态。

## 判题沙箱（核心）

非容器方案：`setuid` 降权到专用 sandbox 用户、清空补充组，seccomp 拦截网络 socket（禁止 `AF_INET`/`AF_INET6`/`AF_NETLINK`），再叠加虚拟内存 / CPU / 文件大小 / 进程数 / 文件描述符限制，防止提交代码触达内网或滥用资源。

## 工程化能力

- 统一 API 响应结构（code/message/requestId/data），方便网关层统一处理
- 按 IP 的分钟窗口限流（Redis `MULTI` 原子操作，避免竞态）
- 审计日志：关键管理与提交动作落库
- Docker Compose 一键启动本地环境，所有服务加 healthcheck

## 四轮安全与工程化修复（FIX_LOG 摘记）

上线前按安全审查清单修了 36 个问题，按轮次分类：

**第一轮（核心安全）**：CORS 从 `*` 改为环境变量白名单；管理员认证从"仅靠邮箱/用户名"改为查库 `role` 字段；JWT Secret 启动时校验非占位符且 ≥32 字符；Redis 加 `--requirepass`；数据库密码硬编码移除；判题链路 `/submit` 补投递 RabbitMQ。

**第二轮（判题链路）**：Worker 断连自动重试；数据库连接池 `ThreadedConnectionPool`；批量操作加事务（BEGIN/COMMIT/ROLLBACK）；周排行榜时区 Bug（`calendar.timegm()` 替代 `time.mktime()`）；Redis 密码启动校验。

**第三轮（Web 加固）**：网关加 `helmet()` 安全响应头、Zod 输入校验；请求体限制 2mb → 256kb；`.env` 用随机强密码。

**第四轮（功能与最佳实践）**：系统状态页加认证头；NavBar 仅 admin 显示管理链接；内部 HTTP 调用全部加 `timeout: 5000`；CORS Credentials 仅在白名单通过时设置；FastAPI 弃用事件迁移到 `lifespan`。

## 结论

把"入口"（网关）、"身份"（认证）、"执行"（判题沙箱）拆开之后，各自可以独立伸缩和加固。沙箱只信任提交的输入并执行，网关不碰执行细节，认证不依赖判题状态。异步链路让判题服务可以水平扩展而不拖垮 API。

安全修复给我的启发：**"能跑"和"能上线"之间隔着一整轮安全审查**——CORS 白名单、JWT Secret 强度、Redis 密码、内部调用超时、请求体限制，这些细节单个都不难，但不列清单逐项过一遍就一定会漏。

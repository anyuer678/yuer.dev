## 软件工程是什么

软件 = 程序 + 数据 + 文档。**软件危机**：规模大、成本高、进度失控、质量低、维护难。软件工程的目标：**在给定成本与进度下，开发出满足用户需求、可靠且易维护的软件**。

**软件特点**：逻辑实体（无磨损但有退化）、需求易变、开发是智力活动、维护成本常高于开发。**软件工程三要素**：过程、方法、工具。

**可信软件**：可靠性、安全性、可用性、可维护性、可移植性等质量属性；可信性关注「行为是否符合预期」。

**工程化思想**：计划驱动、文档化、可重复的过程、质量度量。软件开发的两个基本问题：**做什么（需求）** 与 **怎么做（设计/实现）**。

## 软件生存期过程

软件生存期 = 从概念到退役的全过程。ISO/IEC 12207 把过程分三类：

- **基本过程**：获取、供应、开发、运行、维护
- **支持过程**：文档、配置管理、质量保证、验证、评审
- **组织过程**：管理、改进、培训、基础设施

**开发过程**（狭义的软件开发流程）：

```
可行性研究 → 需求分析 → 概要设计 → 详细设计 → 编码 → 测试 → 部署维护
```

**需求工程**：需求获取 → 需求分析 → 需求规格说明 → 需求验证 → 需求管理。需求分**功能需求**（系统做什么）与**非功能需求**（性能、可用性、安全、可维护性等）。

## 经典过程模型

**瀑布模型**：阶段顺序执行、前一阶段产物是后一阶段输入，文档驱动。优点：阶段清晰、易管理；缺点：**需求变更代价大**、用户直到后期才见到产品、风险后置。适合需求明确稳定的项目。

**原型模型**：先快速构建可运行原型，用户反馈迭代改进，再正式开发。用于需求不明确时**澄清需求**；风险是原型被当作成品。

**增量模型**：把系统分解为多个增量，逐块交付（先核心后外围），每个增量是可运行子集。优点：早交付可用功能、风险分散；缺点：增量划分难、易退化为「边做边改」。

**螺旋模型**：瀑布 + 原型 + 迭代 + **风险分析**，每圈四步：制定计划 → 风险分析 → 工程实施 → 客户评价。适合大型高风险项目；缺点：风险分析要求高、过程复杂。

**演化模型（统一过程 RUP）**：以用例驱动、以架构为中心、迭代增量；阶段：初始（Inception）→ 细化（Elaboration）→ 构造（Construction）→ 移交（Transition）。

## 敏捷开发

**敏捷宣言**：个体与交互 > 过程与工具；可工作软件 > 详尽文档；客户合作 > 合同谈判；响应变化 > 遵循计划。

**核心实践**：短迭代（2-4 周冲刺）、持续交付可运行软件、每日站会、测试驱动、重构、结对编程、现场客户、回顾会议。

**Scrum**：角色（产品负责人 Product Owner、Scrum Master、开发团队）；工件（产品待办列表 Product Backlog、冲刺待办 Sprint Backlog、燃尽图）；事件（冲刺计划会、每日站会、冲刺评审、冲刺回顾）。**冲刺**是固定时长的迭代，结束时交付可用的增量。

**极限编程 XP**：强调工程实践——TDD（先写测试再写实现）、简单设计、持续集成、小步发布、重构、集体代码所有权、可持续节奏。

敏捷适合**需求多变、小团队、快速交付**的场景；不强调前期文档与架构设计。

## 可行性研究

在投入开发前回答：**技术上可行吗？经济上划算吗？法律上允许吗？操作上可用吗？** 五方面：技术、经济、社会（法律）、操作、进度。

- 技术可行性：现有技术能否实现
- 经济可行性：成本效益分析（投资回收期、净现值）
- 法律可行性：版权、合规
- 操作可行性：用户能否接受、组织能否支持

输出**可行性研究报告**，是立项决策的依据。

## 软件测试

**测试目的**：发现缺陷（而不是证明没缺陷）。**测试不可能穷尽**，只能抽样验证。

**测试层次**（V 模型）：

```
需求 → 验收测试
概要设计 → 系统测试
详细设计 → 集成测试
编码 → 单元测试
```

- **单元测试**：最小模块（函数/类），白盒为主（语句/分支/路径覆盖）
- **集成测试**：模块间接口，自顶向下（需桩模块）/自底向上（需驱动模块）/混合
- **系统测试**：整体行为与非功能（性能、压力、安全、兼容性）
- **验收测试**：用户确认是否满足需求（α 测试在开发方现场、β 测试在用户环境）

**黑盒 vs 白盒**：黑盒（等价类划分、边界值分析、因果图、判定表）不关心内部实现，按规格测功能；白盒（语句覆盖、判定覆盖、条件覆盖、路径覆盖）依据代码结构设计用例。**覆盖率**从低到高：语句 < 判定 < 条件 < 路径。

**回归测试**：修改后重跑旧用例，确认没破坏已有功能。**缺陷管理**：缺陷报告 → 分类分级 → 修复 → 验证 → 关闭。

## 软件维护

维护类型：**改正性**（修 bug）、**适应性**（环境变化）、**完善性**（增加/改进功能，占比最大）、**预防性**（防患于未然）。维护成本高的根源：文档缺失、设计糟糕、需求蔓延。

**可维护性**：可理解性、可修改性、可测试性、可移植性。好的设计（模块化、低耦合高内聚、注释规范）直接降低维护成本。

## 软件项目管理

**项目计划**三件事：估算（规模、工作量、进度）、成本效益分析（成本、效益、投资回收期/回收率、纯收入）、进度安排（甘特图、PERT 图、关键路径法 CPM）。PERT 图能看清任务依赖和关键路径——关键路径上的任务延误直接拖慢整个项目。

**项目组织**三种模式：

- **民主制程序员组**：无正式负责人，全员平等讨论，适合小型探索性项目
- **主程序员组**：主程序员负责整体设计决策，其他成员协助，效率高但对个人依赖大
- **现代程序员组**：技术负责人 + 管理负责人分工，兼顾技术决策与资源协调，实际项目最常见

**项目追踪与控制**：进度追踪（实际 vs 计划）、质量追踪（缺陷密度、测试覆盖率）、成本追踪（预算消耗）、范围控制（防需求蔓延）、风险控制（识别 → 评估 → 应对）。

## 速记口诀

- 软件 = 程序 + 数据 + 文档；工程三要素 = 过程、方法、工具
- 模型对比：瀑布稳但怕变，原型清需求，增量早交付，螺旋管风险，敏捷响应变化
- 测试层次：单、集、系、验；黑盒测功能，白盒测结构
- 维护四类：改（bug）适（环境）完（功能）防（预防）
- 易错点：测试是为了发现缺陷而非证明正确；敏捷 ≠ 无文档，只是轻文档

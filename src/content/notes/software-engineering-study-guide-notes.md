#### 2.2 软件工程经典生存周期模型深度解析
- 瀑布模型（Waterfall Model）
  - 提出时间：1970年，Winston Royce
  - 特点：
    - 线性顺序的开发过程
    - 每个阶段完成后，才能进入下一个阶段
    - 每个阶段有明确的输入和输出
    - 强调文档的完整性
  - 阶段划分：
    1. 需求分析与规格说明
    2. 系统设计与软件设计
    3. 编码与单元测试
    4. 集成与系统测试
    5. 运行与维护
  - 优点：
    - 简单易用，易于理解和管理
    - 强调阶段评审，保证质量
    - 文档驱动，便于维护
  - 缺点：
    - 线性过程，难以适应需求变化
    - 后期才能看到产品，风险较大
    - 不适合需求不明确的项目
  - 适用场景：
    - 需求明确、稳定的项目
    - 小型、简单的项目
    - 对质量要求极高的项目（如航天、医疗）
- 原型模型（Prototype Model）
  - 核心思想：快速构建一个可运行的原型，通过用户反馈逐步完善
  - 类型：
    - 抛弃式原型（Throwaway Prototype）
      - 快速构建，用于验证需求
      - 验证后抛弃，重新开发
    - 演化式原型（Evolutionary Prototype）
      - 逐步完善原型，最终成为产品
  - 优点：
    - 尽早获得用户反馈
    - 降低需求不明确的风险
    - 提高用户满意度
  - 缺点：
    - 可能导致需求蔓延（Scope Creep）
    - 原型可能影响最终产品的设计
    - 管理难度较大
  - 适用场景：
    - 需求不明确的项目
    - 用户界面复杂的项目
    - 需要快速验证概念的项目
- 增量模型（Incremental Model）
  - 核心思想：将软件产品分解为多个增量，逐个交付
  - 特点：
    - 第一个增量是核心功能
    - 后续增量逐步增加功能
    - 每个增量都是可运行的
  - 优点：
    - 早期可以交付部分功能，获得反馈
    - 降低开发风险
    - 灵活适应需求变化
    - 资源分配灵活
  - 缺点：
    - 需要良好的架构设计
    - 增量之间可能存在接口问题
    - 可能导致系统架构退化
  - 适用场景：
    - 需求可能变化的项目
    - 需要早期交付的项目
    - 大型复杂项目
- 螺旋模型（Spiral Model）
  - 提出时间：1988年，Barry Boehm
  - 核心思想：结合瀑布模型和原型模型，强调风险分析
  - 四个象限：
    1. 制定计划：确定目标、方案、约束
    2. 风险分析：分析风险，制定应对措施
    3. 开发实施：开发和测试
    4. 客户评估：用户评估，提出反馈
  - 特点：
    - 迭代过程，每次迭代增加风险控制
    - 强调风险分析和管理
    - 可以结合多种开发方法
  - 优点：
    - 强调风险分析，降低风险
    - 灵活适应变化
    - 适合大型复杂项目
  - 缺点：
    - 复杂，难以管理
    - 需要丰富的风险分析经验
    - 成本较高，周期较长
  - 适用场景：
    - 大型、复杂、高风险的项目
    - 需求不确定的项目
    - 对风险敏感的项目
- 喷泉模型（Fountain Model）
  - 提出时间：1990年，针对面向对象开发
  - 核心思想：迭代和无间隙的开发过程
  - 特点：
    - 各个阶段可以重叠、并行
    - 强调对象的复用
    - 迭代和增量开发
  - 优点：
    - 适合面向对象开发
    - 提高开发效率
    - 支持复用
  - 缺点：
    - 管理难度大
    - 需要严格的文档管理
  - 适用场景：
    - 面向对象的软件开发项目
- V模型（V-Model）
  - 特点：瀑布模型的变种，强调测试与开发的对应关系
  - 对应关系：
    - 需求分析 → 验收测试
    - 系统设计 → 系统测试
    - 详细设计 → 集成测试
    - 编码 → 单元测试
  - 优点：
    - 强调测试的重要性
    - 测试与开发并行
    - 清晰的对应关系
  - 缺点：
    - 仍然是线性过程
    - 难以适应变化
- 各模型比较总结
  | 模型 | 特点 | 优点 | 缺点 | 适用场景 |
  |------|------|------|------|----------|
  | 瀑布模型 | 线性、文档驱动 | 简单、易管理 | 不灵活、风险高 | 需求明确的小项目 |
  | 原型模型 | 快速原型、用户反馈 | 降低风险、用户满意 | 需求蔓延 | 需求不明确项目 |
  | 增量模型 | 增量交付、迭代 | 早期交付、灵活 | 架构要求高 | 需求变化的项目 |
  | 螺旋模型 | 风险驱动、迭代 | 风险控制好 | 复杂、成本高 | 大型高风险项目 |
  | 喷泉模型 | 面向对象、无间隙 | 效率高、支持复用 | 管理难 | 面向对象项目 |

#### 2.3 敏捷软件开发过程深度解析
- **敏捷开发宣言（2001年）**
  - 个体和互动 高于 流程和工具
  - 可工作的软件 高于 详尽的文档
  - 客户合作 高于 合同谈判
  - 响应变化 高于 遵循计划
- **敏捷开发十二原则**
  1. 我们最优先要做的是通过尽早的、持续的交付有价值的软件来使客户满意
  2. 即使到了开发的后期，也欢迎改变需求。敏捷过程利用变化来为客户创造竞争优势
  3. 经常性地交付可以工作的软件，交付的间隔可以从几周到几个月，交付的时间间隔越短越好
  4. 在整个项目开发期间，业务人员和开发者必须天天在一起工作
  5. 围绕被激励起来的个体来构建项目，给他们提供所需的环境和支持，并且信任他们能够完成工作
  6. 在团队内部，最具有效果并且富有效率的传递信息的方法，就是面对面的交谈
  7. 可工作的软件是进度的首要度量标准
  8. 敏捷过程提倡可持续的开发速度。责任人、开发者和用户应该能够保持一个长期的、恒定的开发速度
  9. 不断地关注优秀的技术和好的设计能增强敏捷能力
  10. 简单-使未完成的工作最大化的艺术-是根本的
  11. 最好的架构、需求和设计出自于自组织的团队
  12. 每隔一定时间，团队会在如何才能更有效地工作方面进行反省，然后相应地对自己的行为进行调整
- **Scrum框架详解**
  - **角色**
    - 产品负责人（Product Owner）：负责产品待办列表，确定优先级，最大化产品价值
    - Scrum Master：服务式领导，移除障碍，促进协作，确保Scrum实践被遵循
    - 开发团队（Development Team）：自组织、跨职能，5-9人，负责交付可工作的产品增量
  - **事件**
    - Sprint（冲刺）：时间盒为1-4周，期间开发可工作的、"完成的"产品增量
    - Sprint计划会议（Sprint Planning）：
      - 时间盒：8小时（4周Sprint）
      - 议题1：我们能完成什么？
      - 议题2：我们如何完成选定的工作？
      - 产出：Sprint目标和Sprint待办列表
    - 每日站会（Daily Scrum）：
      - 时间盒：15分钟
      - 三个问题：
        1. 昨天我完成了什么帮助团队达成Sprint目标的工作？
        2. 今天我计划做什么来帮助团队达成Sprint目标的工作？
        3. 我看到了什么障碍阻碍我或团队达成Sprint目标？
      - 目的：同步进度，识别障碍，快速调整
    - Sprint评审会议（Sprint Review）：
      - 时间盒：4小时（4周Sprint）
      - 内容：展示产品增量，收集反馈，调整产品待办列表
      - 参与方：Scrum团队和利益相关者
    - Sprint回顾会议（Sprint Retrospective）：
      - 时间盒：3小时（4周Sprint）
      - 目的：改进过程，持续优化
      - 三个问题：
        1. 哪些做得好？
        2. 哪些可以改进？
        3. 我们如何改进？
  - **工件**
    - 产品待办列表（Product Backlog）：所有产品功能的有序列表，持续细化和更新
    - Sprint待办列表（Sprint Backlog）：Sprint中选定的产品待办列表项加上开发计划
    - 产品增量（Increment）：Sprint的产出，可工作的、"完成的"产品版本
- **极限编程（eXtreme Programming, XP）详解**
  - **核心价值观**
    - 沟通（Communication）
    - 简单（Simplicity）
    - 反馈（Feedback）
    - 勇气（Courage）
    - 尊重（Respect）
  - **主要实践**
    - 客户团队（Whole Team）：客户与开发团队一起工作
    - 规划游戏（Planning Game）：业务人员和开发人员共同规划
    - 小发布（Small Releases）：频繁发布小版本
    - 简单设计（Simple Design）：只满足当前需求的最简单设计
    - 结对编程（Pair Programming）：两个程序员共用一台电脑
    - 测试驱动开发（Test-Driven Development, TDD）：先写测试，再写代码
    - 重构（Refactoring）：不改变外部行为的情况下优化内部结构
    - 持续集成（Continuous Integration）：频繁集成，持续验证
    - 集体代码所有权（Collective Code Ownership）：任何人可以修改任何代码
    - 编码标准（Coding Standards）：统一的编码规范
    - 隐喻（Metaphor）：用简单故事描述系统
    - 可持续的节奏（Sustainable Pace）：保持可长期维持的工作节奏
  - **TDD（测试驱动开发）详细步骤**
    1. 红（Red）：写一个失败的测试用例
    2. 绿（Green）：写最简单的代码让测试通过
    3. 重构（Refactor）：优化代码，保持测试通过
    - 示例（Java + JUnit）：
      ```java
      // 测试类
      import static org.junit.Assert.*;
      import org.junit.Test;
      
      public class CalculatorTest {
          @Test
          public void testAdd() {
              Calculator calculator = new Calculator();
              int result = calculator.add(2, 3);
              assertEquals(5, result);
          }
          
          @Test
          public void testSubtract() {
              Calculator calculator = new Calculator();
              int result = calculator.subtract(5, 3);
              assertEquals(2, result);
          }
      }
      
      // 实现类
      public class Calculator {
          public int add(int a, int b) {
              return a + b;
          }
          
          public int subtract(int a, int b) {
              return a - b;
          }
      }
      ```
- **看板方法（Kanban）详解**
  - **核心原则**
    - 可视化工作流（Visualize the workflow）
    - 限制在制品（Limit WIP, Work In Progress）
    - 度量和管理流动（Measure and manage flow）
    - 制定明确的流程策略（Make process policies explicit）
    - 实现反馈循环（Implement feedback loops）
    - 协作改进，实验演进（Improve collaboratively, evolve experimentally）
  - **看板实践**
    - 看板墙：分为"待办"、"进行中"、"已完成"等列
    - 卡片：代表任务，包含描述、负责人、优先级等信息
    - WIP限制：每列设置最大在制品数量
    - 拉动系统：只有下游有能力时才拉动上游工作
  - **与Scrum的区别**
    - Scrum：时间盒驱动，有Sprint计划、每日站会、评审、回顾
    - Kanban：持续流动，无迭代，无固定角色
- **Scrum与Kanban结合：Scrumban**
  - 使用Scrum的事件和角色
  - 使用看板的可视化和WIP限制

#### 3.1 软件项目可行性研究内容与步骤深度解析
- **可行性研究的内容**
  - **技术可行性（Technical Feasibility）**
    - 现有技术是否能实现系统
    - 技术人员的技术水平
    - 技术风险评估
    - 技术成熟度和可用性
    - 评估维度：
      1. 技术方案的成熟度
      2. 开发团队的技术能力
      3. 硬件、软件环境的可用性
      4. 技术风险的可控性
  - **经济可行性（Economic Feasibility）**
    - 成本估算
    - 效益分析
    - 投资回报率（ROI）
    - 净现值（NPV）
    - 投资回收期
    - 成本构成：
      - 开发成本：人员工资、硬件软件采购、培训
      - 运营成本：维护费、电费、人员工资
      - 其他成本：差旅费、咨询费
    - 效益构成：
      - 经济效益：直接收入、成本节约、效率提升
      - 社会效益：品牌价值、用户满意度、社会影响
  - **操作可行性（Operational Feasibility）**
    - 用户对系统的接受程度
    - 现有管理制度的兼容性
    - 人员培训计划
    - 法律和政策合规性
  - **法律可行性（Legal Feasibility）**
    - 知识产权
    - 合同条款
    - 法律法规合规
- **可行性研究的步骤**
  1. 复查系统规模和目标
  2. 研究目前正在使用的系统
  3. 导出新系统的高层逻辑模型
  4. 重新定义问题
  5. 导出和评价供选择的方案
  6. 推荐一个方案并说明理由
  7. 草拟开发计划
  8. 书写文档提交审查
- **可行性研究报告的编写**
  - **报告结构**
    1. 引言
    2. 可行性研究的前提
    3. 对现有系统的分析
    4. 所建议的系统
    5. 可选择的其他系统方案
    6. 投资及效益分析
    7. 社会因素方面的可行性
    8. 结论
  - **经济可行性分析示例**
    - 投资回收期计算：
      - 累计净现金流量首次为正的年份 - 1 + 上年累计净现金流量绝对值 / 当年净现金流量
    - NPV（净现值）公式：
      - NPV = Σ (Ct / (1 + r)^t)，其中Ct为第t年净现金流量，r为贴现率
    - ROI（投资回报率）公式：
      - ROI = (总收益 - 总成本) / 总成本 × 100%
- **可行性研究的评估**
  - 技术评估：技术专家评审
  - 经济评估：财务分析
  - 操作评估：用户反馈
  - 综合评估：决策委员会

#### 3.2 软件系统功能分析深度解析
- **需求的层次**
  - **业务需求（Business Requirements）**
    - 组织的高层目标
    - 示例："提高客户满意度30%"
  - **用户需求（User Requirements）**
    - 用户完成任务的能力
    - 示例："用户可以查询订单状态"
  - **功能需求（Functional Requirements）**
    - 系统必须实现的功能
    - 示例："系统显示订单编号、日期、状态和金额"
  - **非功能需求（Non-functional Requirements）**
    - 系统的质量属性
- **功能需求分析**
  - **功能需求的特征**
    - 完整性（Complete）
    - 一致性（Consistent）
    - 可测试性（Testable）
    - 清晰性（Clear）
    - 可追踪性（Traceable）
  - **功能需求的描述方式**
    - 用例（Use Case）
    - 用户故事（User Story）
    - 功能规格说明书
  - **用户故事格式**
    - "作为一个[角色]，我想要[功能]，以便[价值]"
    - 示例："作为一个客户，我想要查看我的订单历史，以便了解我的购买记录"
    - 验收标准（Acceptance Criteria）：
      - GIVEN（给定）：某个前置条件
      - WHEN（当）：执行某个操作
      - THEN（那么）：预期结果
      - 示例：
        - GIVEN 用户已登录
        - WHEN 用户点击"订单历史"
        - THEN 显示用户最近12个月的所有订单
- **非功能需求分析**
  - **性能需求（Performance Requirements）**
    - 响应时间："系统响应时间不超过2秒"
    - 吞吐量："系统每秒处理1000个请求"
    - 资源利用率："CPU利用率不超过80%"
    - 容量："支持10万并发用户"
  - **安全性需求（Security Requirements）**
    - 认证："用户必须使用用户名和密码登录"
    - 授权："只有管理员可以删除用户"
    - 加密："密码使用SHA-256哈希存储"

#### 3.3 软件系统故障分析深度解析
- **故障树分析（Fault Tree Analysis, FTA）**
  - **定义**：一种自上而下的演绎分析方法，用于分析系统故障的原因
  - **符号**
    - 顶事件（Top Event）：要分析的故障
    - 中间事件（Intermediate Event）：故障的中间原因
    - 基本事件（Basic Event）：不能再分解的原因
    - 与门（AND Gate）：所有输入都发生，输出才发生
    - 或门（OR Gate）：任一输入发生，输出就发生
  - **分析步骤**
    1. 确定顶事件
    2. 构建故障树
    3. 定性分析：识别最小割集
    4. 定量分析：计算顶事件发生概率
  - **示例**：系统停机故障树
    - 顶事件：系统停机
      - 或门
        - 中间事件：硬件故障
          - 或门
            - 基本事件：服务器故障
            - 基本事件：网络故障
        - 中间事件：软件故障
          - 或门
            - 基本事件：应用程序崩溃
            - 基本事件：数据库故障
- **失效模式与影响分析（Failure Mode and Effects Analysis, FMEA）**
  - **定义**：一种自下而上的归纳分析方法，用于识别潜在失效及其影响
  - **类型**
    - 设计FMEA（DFMEA）：分析设计阶段的失效
    - 过程FMEA（PFMEA）：分析制造/装配过程的失效
    - 系统FMEA（SFMEA）：分析系统级的失效
  - **FMEA表格**
    | 部件 | 功能 | 失效模式 | 失效影响 | 严重度(S) | 原因 | 频度(O) | 当前控制 | 探测度(D) | RPN | 建议措施 | 责任人 | 完成日期 |
  - **评分标准**
    - 严重度（Severity, S）：1-10分，10最严重
    - 频度（Occurrence, O）：1-10分，10最频繁
    - 探测度（Detection, D）：1-10分，10最难探测
    - 风险优先数（RPN）= S × O × D
- **故障分析的应用**
  - 可靠性设计
  - 风险评估
  - 维护策略制定
  - 安全分析
- **故障预防措施**
  - 冗余设计
  - 容错设计
  - 预防性维护
  - 监控和告警
  - 快速恢复

#### 3.4 软件项目成本估计深度解析
- **成本估计方法**
  - **类比估计（Analogous Estimating）**
    - 基于类似项目的实际成本进行估计
    - 优点：简单快速、成本低
    - 缺点：准确度依赖于项目相似度
    - 适用：项目早期、信息有限时
  - **参数估计（Parametric Estimating）**
    - 使用统计关系进行估计
    - 示例：代码行数 × 每代码行成本
    - 优点：准确度较高
    - 缺点：需要历史数据
  - **自下而上估计（Bottom-up Estimating）**
    - 先估计每个工作包的成本，再汇总
    - 优点：准确度高
    - 缺点：耗时、成本高
    - 适用：详细设计完成后
  - **三点估计（Three-Point Estimating）**
    - 乐观估计（O）、最可能估计（M）、悲观估计（P）
    - 三角分布：E = (O + M + P) / 3
    - Beta分布（PERT）：E = (O + 4M + P) / 6
- **COCOMO模型（构造性成本模型）详解**
  - **基本COCOMO（Basic COCOMO）**
    - 有机型（Organic）：小团队、熟悉技术
      - Effort = 2.4 × (KLOC)^1.05 人月
      - Duration = 2.5 × (Effort)^0.38 月
    - 半独立型（Semidetached）：中等规模、部分熟悉
      - Effort = 3.0 × (KLOC)^1.12 人月
      - Duration = 2.5 × (Effort)^0.35 月
    - 嵌入型（Embedded）：复杂、硬件约束多
      - Effort = 3.6 × (KLOC)^1.20 人月
      - Duration = 2.5 × (Effort)^0.32 月
  - **中间COCOMO（Intermediate COCOMO）**
    - 引入成本驱动因子（Cost Drivers）
    - 15个因子：产品属性、硬件属性、人员属性、项目属性
    - Effort = a × (KLOC)^b × EAF（工作量调整因子）
  - **详细COCOMO（Detailed COCOMO）**
    - 分阶段调整因子
- **功能点分析（Function Point Analysis, FPA）**
  - **功能点计数**
    - 外部输入（EI）
    - 外部输出（EO）
    - 外部查询（EQ）
    - 内部逻辑文件（ILF）
    - 外部接口文件（EIF）
  - **复杂度权重**
    - 简单、平均、复杂
  - **未调整功能点（UFP）**
  - **调整因子（VAF）**：14个通用系统特性
  - **调整后功能点（AFP）= UFP × VAF**
- **成本控制**
  - **挣值管理（Earned Value Management, EVM）**
    - PV（计划价值，Planned Value）：计划完成工作的预算
    - EV（挣值，Earned Value）：实际完成工作的预算
    - AC（实际成本，Actual Cost）：实际花费的成本
    - 进度偏差（SV）= EV - PV
    - 成本偏差（CV）= EV - AC
    - 进度绩效指数（SPI）= EV / PV
    - 成本绩效指数（CPI）= EV / AC
    - 完工估算（EAC）= BAC / CPI（典型偏差）
    - 完工尚需估算（ETC）= EAC - AC
  - **成本控制措施**
    - 变更管理
    - 资源优化
    - 供应商谈判
    - 范围控制

#### 3.5 软件项目效益分析深度解析
- **经济效益分析**
  - **投资回报率（Return on Investment, ROI）**
    - ROI = (总收益 - 总成本) / 总成本 × 100%
    - 示例：投资100万，收益150万，ROI = 50%
  - **净现值（Net Present Value, NPV）**
    - NPV = Σ (Ct / (1 + r)^t) - 初始投资
    - Ct：第t年的净现金流量
    - r：贴现率
    - 决策规则：NPV > 0，项目可行
  - **内部收益率（Internal Rate of Return, IRR）**
    - 使NPV = 0的贴现率
    - 决策规则：IRR > 基准收益率，项目可行
  - **投资回收期（Payback Period）**
    - 静态投资回收期：不考虑资金时间价值
    - 动态投资回收期：考虑资金时间价值
    - 决策规则：投资回收期 < 基准回收期，项目可行
  - **获利指数（Profitability Index, PI）**
    - PI = 未来现金流量现值 / 初始投资
    - 决策规则：PI > 1，项目可行
- **社会效益分析**
  - 用户满意度提升
  - 品牌价值增加
  - 就业机会创造
  - 行业标准推动
  - 环保效益
- **效益评估方法**
  - 成本效益分析（Cost-Benefit Analysis, CBA）
  - 成本效果分析（Cost-Effectiveness Analysis, CEA）
  - 多准则决策分析（Multi-Criteria Decision Analysis, MCDA）
- **项目风险分析**
  - **风险识别**
    - 技术风险
    - 市场风险
    - 财务风险
    - 法律风险
    - 运营风险
  - **风险评估**
    - 定性评估：风险矩阵
    - 定量评估：期望值、敏感性分析
  - **风险应对**
    - 规避（Avoid）：消除风险
    - 转移（Transfer）：转移给第三方（保险、外包）
    - 减轻（Mitigate）：降低概率或影响
    - 接受（Accept）：接受风险

#### 8.1-8.2 软件测试深度解析
- 软件测试的基本概念
  - 软件测试的定义
    - 为了发现程序中的错误而执行程序的过程
    - 目的：发现缺陷、评估质量、提供信心
  - 软件测试的目标
    - 发现尽可能多的缺陷
    - 验证软件是否满足需求
    - 评估软件质量
    - 预防缺陷
  - 软件测试的原则
    - 测试只能证明缺陷存在，不能证明缺陷不存在
    - 穷举测试是不可能的
    - 尽早进行测试
    - 缺陷集群性（二八定律：80%的缺陷集中在20%的模块）
    - 杀虫剂悖论：测试用例需要定期更新
    - 测试依赖于上下文
    - 没有错误的谬论：即使没有发现缺陷，也不代表软件完美
  - 软件测试的心理学
    - 测试者的心态：破坏性的、寻找缺陷
    - 开发者的心态：建设性的、证明正确
    - 独立测试的重要性
    - 测试与调试的区别
- 软件测试策略详解
  - 测试的级别（V模型）
    - 单元测试（Unit Testing）
      - 测试对象：模块、函数、类

    - 集成测试（Integration Testing）

      - 测试方法：白盒+黑盒
      - 目标：发现接口缺陷
    - 系统测试（System Testing）
      - 测试对象：整个系统
      - 测试依据：需求规格说明书
      - 测试方法：黑盒测试
      - 目标：验证系统是否满足需求
    - 验收测试（Acceptance Testing）
      - 测试对象：整个系统
      - 测试依据：用户需求
      - 测试方法：黑盒测试
      - 目标：确认系统是否满足用户需求
- 测试用例设计详解
  - 测试用例的定义
    - 为特定目标设计的一组测试输入、执行条件和预期结果

#### 8.3-8.4 软件测试深度解析
- 黑盒测试（Black-box Testing）详解
  - 定义：不考虑内部结构，只关注输入和输出
  - 又称：功能测试、数据驱动测试
  - 等价类划分（Equivalence Partitioning）
    - 定义：将输入域划分为若干等价类，从每个等价类中选取代表性数据作为测试用例
    - 有效等价类：合理的、有意义的输入
    - 无效等价类：不合理的、无意义的输入
    - 设计步骤：
      1. 确定等价类
      2. 为每个等价类编号
      3. 设计测试用例覆盖有效等价类
      4. 设计测试用例覆盖无效等价类
    - 示例：输入1-100的整数
      - 有效等价类：1≤x≤100
      - 无效等价类：x<1、x>100、非整数
  - 边界值分析（Boundary Value Analysis, BVA）
    - 定义：针对输入或输出的边界值设计测试用例
    - 原理：缺陷往往出现在边界处
    - 设计方法：
      - 最小值、略大于最小值、正常值、略小于最大值、最大值
      - 对于n个变量，有4n+1个测试用例
    - 示例：输入1-100的整数
      - 测试值：0、1、2、50、99、100、101
  - 因果图（Cause-Effect Graphing）
    - 定义：分析输入条件之间的因果关系和约束关系
    - 步骤：
      1. 分析原因和结果
      2. 画出因果图
      3. 转换为决策表
      4. 生成测试用例
    - 适合：多条件组合的情况
  - 决策表（Decision Table）
    - 定义：以表格形式表示条件和动作的对应关系
    - 组成：
      - 条件桩：列出所有条件
      - 动作桩：列出所有动作
      - 条件项：条件的各种组合
      - 动作项：对应的动作
    - 优点：完整、清晰、无遗漏
  - 错误推测法（Error Guessing）
    - 定义：基于经验和直觉推测可能出现的错误
    - 优点：发现一些特殊的缺陷
    - 缺点：依赖经验，无法保证覆盖
- 白盒测试（White-box Testing）详解
  - 定义：考虑内部结构，测试程序的执行路径
  - 又称：结构测试、逻辑驱动测试、玻璃盒测试
  - 语句覆盖（Statement Coverage）
    - 定义：使程序中每条语句至少执行一次
    - 公式：被执行语句数 / 总语句数 × 100%
    - 缺点：最弱的覆盖，无法发现逻辑错误
  - 判定覆盖（Decision Coverage）
    - 又称：分支覆盖
    - 定义：使程序中每个判定的真假分支至少执行一次
    - 公式：被执行判定数 / 总判定数 × 100%
    - 比语句覆盖强，但仍不充分
  - 条件覆盖（Condition Coverage）
    - 定义：使程序中每个判定中的每个条件的可能取值至少出现一次
    - 比判定覆盖强，但不一定覆盖判定
  - 判定-条件覆盖（Decision-Condition Coverage）
    - 定义：同时满足判定覆盖和条件覆盖
    - 比前两者强，但仍有遗漏
  - 条件组合覆盖（Multiple Condition Coverage）
    - 定义：使程序中每个判定的所有条件组合至少出现一次
    - 覆盖很强，但测试用例数量多
  - 路径覆盖（Path Coverage）
    - 定义：使程序中所有可能的路径至少执行一次
    - 最强的覆盖，但循环多的时候无法实现
  - 基路径测试（Basis Path Testing）
    - 提出：Tom McCabe
    - 方法：
      1. 画出程序流程图
      2. 计算环形复杂度
      3. 确定独立路径集合
      4. 设计测试用例覆盖每条独立路径
    - 环形复杂度计算：
      - V(G) = 区域数
      - V(G) = E - N + 2（E=边数，N=节点数）
      - V(G) = P + 1（P=判定节点数）
- 测试覆盖率（Test Coverage）详解
  - 定义：测试覆盖的程度
  - 作用：评估测试的充分性
  - 常用覆盖率指标：
    - 语句覆盖率
    - 分支覆盖率
    - 条件覆盖率
    - 路径覆盖率
    - 功能覆盖率
- 测试工具简介
  - 单元测试工具：JUnit、TestNG、pytest、unittest
  - 性能测试工具：JMeter、LoadRunner、Gatling
  - 接口测试工具：Postman、SoapUI、RestAssured
  - 自动化测试工具：Selenium、Appium、Cypress
  - 测试管理工具：TestLink、Zephyr、TestRail
#### 8.5-8.10 软件测试深度解析
- 单元测试（Unit Testing）详解
  - 单元测试的目标
    - 验证单元功能正确性
    - 发现单元内部的缺陷

    - 配合黑盒测试
    - 使用测试驱动开发（TDD）
  - 测试驱动开发（Test-Driven Development, TDD）
    - 核心思想：先写测试，再写代码
    - 步骤：
      1. 红：写一个失败的测试
      2. 绿：写最简单的代码让测试通过
      3. 重构：优化代码，保持测试通过
    - 优点：
      - 代码质量高
      - 测试覆盖率高
      - 重构安全
      - 文档完善
  - 单元测试框架
    - Java：JUnit、TestNG
    - Python：pytest、unittest
    - JavaScript：Jest、Mocha
    - C#：NUnit、xUnit
  - Mock对象（模拟对象）
    - 作用：隔离被测单元
    - 框架：Mockito、EasyMock、PowerMock
- 集成测试（Integration Testing）详解
  - 集成测试的目标
    - 发现模块间接口的缺陷
    - 验证模块协作的正确性
  - 集成测试的策略
    - 自顶向下集成（Top-down Integration）
      - 从主控模块开始，逐步集成
      - 使用桩模块（Stub）模拟下层模块
      - 优点：早期验证主要控制路径
      - 缺点：桩模块开发复杂
    - 自底向上集成（Bottom-up Integration）
      - 从最底层模块开始，逐步集成
      - 使用驱动模块（Driver）模拟上层模块
      - 优点：底层模块测试充分
      - 缺点：最后才能看到系统
    - 三明治集成（Sandwich Integration）
      - 结合自顶向下和自底向上
      - 从中间层开始，双向集成
      - 优点：兼顾两者优点
    - 大爆炸集成（Big Bang Integration）
      - 所有模块一次性集成
      - 优点：简单
      - 缺点：定位缺陷困难
  - 集成测试的内容
    - 接口数据传递
    - 接口调用顺序
    - 数据一致性
    - 资源竞争
- 系统测试（System Testing）详解
  - 系统测试的目标
    - 验证系统是否满足需求规格
    - 发现系统级的缺陷
  - 系统测试的类型
    - 功能测试（Functional Testing）
      - 验证功能是否满足需求
      - 主要方法：黑盒测试
    - 性能测试（Performance Testing）
      - 负载测试（Load Testing）：正常负载下的性能
      - 压力测试（Stress Testing）：极限负载下的性能
      - 稳定性测试（Soak Testing）：长时间运行的稳定性
      - 并发测试（Concurrency Testing）：多用户并发
      - 指标：响应时间、吞吐量、资源利用率
    - 安全性测试（Security Testing）
      - 验证系统的安全性
      - 内容：认证、授权、加密、漏洞扫描
      - 方法：渗透测试、安全审计
    - 兼容性测试（Compatibility Testing）
      - 验证在不同环境下的兼容性
      - 内容：浏览器、操作系统、设备
    - 可用性测试（Usability Testing）
      - 验证用户体验
      - 内容：易用性、易学性、用户满意度
    - 可靠性测试（Reliability Testing）
      - 验证系统的可靠性
      - 指标：MTBF（平均故障间隔时间）、MTTR
    - 恢复性测试（Recovery Testing）
      - 验证系统从故障中恢复的能力
      - 内容：数据备份、故障转移
- 验收测试（Acceptance Testing）详解
  - 验收测试的目标
    - 确认系统是否满足用户需求
    - 决定是否接受系统
  - 验收测试的类型
    - α测试（Alpha Testing）
      - 开发环境下，用户进行的测试
      - 开发人员在场
    - β测试（Beta Testing）
      - 用户环境下，用户进行的测试
      - 开发人员不在场
      - 收集用户反馈
    - 合同验收测试（Contract Acceptance Testing）
      - 按照合同条款进行的验收
    - 法规验收测试（Regulatory Acceptance Testing）
      - 按照法律法规进行的验收
  - 验收测试的内容
    - 功能验收
    - 性能验收
    - 文档验收
    - 培训验收
- 测试自动化（Test Automation）详解
  - 测试自动化的定义
    - 使用工具或脚本自动执行测试
  - 测试自动化的优点
    - 提高测试效率

## 六、速记宝典（口诀 + 对比表 + 流程速查）

### 6.1 软件工程核心概念速记

**软件四大特性**：「**复不见变服**」
| 特性 | 含义 | 速记 |
|------|------|------|
| **复**杂性 | 软件是复杂的逻辑系统 | 代码量越大越难管 |
| **不**可见性 | 软件看不见摸不着 | 不像房子有图纸 |
| **变**易性 | 需求经常变化 | 最大的挑战 |
| **服**从性 | 软件必须适应硬件/环境 | 不能独立存在 |

**软件危机**：成本超预算、进度延迟、质量不达标、维护困难
- 记忆：**"软件危机=花太多、做太慢、质量差、改不动"**

---

### 6.2 软件生存周期模型速记

**核心模型对比**：

| 模型 | 特点 | 适用场景 | 一句话 |
|------|------|---------|--------|
| 瀑布模型 | 线性顺序，不可逆 | 需求明确稳定 | **"一路走到黑"** |
| 原型模型 | 快速做样品，反馈迭代 | 需求不明确 | **"先做样品给你看"** |
| 增量模型 | 分模块逐步交付 | 核心功能先行 | **"分期付款"** |
| 螺旋模型 | 每轮评估风险 | 高风险大项目 | **"边做边防风险"** |
| 敏捷开发 | 短迭代、快速响应 | 需求常变 | **"小步快跑"** |

**瀑布模型五阶段**：「**需→设→编→测→维**」
```
需求分析 → 系统/软件设计 → 编码测试 → 集成测试 → 运行维护
```

---

### 6.3 敏捷开发速记

**敏捷宣言四句话**：
```
个体和互动 > 流程和工具
可工作的软件 > 面面俱到的文档
客户合作     > 合同谈判
响应变化     > 遵循计划
```
- 记忆：**"人>流程，软件>文档，客户>合同，变>死"**

**Scrum三角色三仪式**：
| 三角色 | 职责 | 三仪式 | 内容 |
|--------|------|--------|------|
| Product Owner | 定义需求，排优先级 | Sprint计划会 | 定这轮做什么 |
| Scrum Master | 保证流程，清除障碍 | 每日站会 | 15分钟，三个问题 |
| Dev Team | 开发交付 | Sprint回顾会 | 复盘改进 |

**三个每日站会问题**：「**昨天干了啥，今天要干啥，遇到啥困难**」

---

### 6.4 项目管理核心速记

**可行性研究四方面**：「**技经操法**」
| 方面 | 内容 |
|------|------|
| **技**术可行性 | 技术能做吗？ |
| **经**济可行性 | 钱够吗？划算吗？ |
| **操**作可行性 | 用户会用吗？ |
| **法**律可行性 | 合法吗？侵权吗？ |

**项目计划三要素**：「**时质本**」= 时间、质量、成本（铁三角，动一个牵全部）

**WBS**（工作分解结构）：把大任务拆成小任务
- 记忆：**"大事化小，小事化了"**

---

### 6.5 需求分析速记

**需求分析的任务**：「**定功能、建模型、写规格**」

**需求分类**：
| 类型 | 含义 | 记忆 |
|------|------|------|
| 功能需求 | 系统要做什么 | **"能干啥"** |
| 非功能需求 | 性能、安全、可用性... | **"干得怎么样"** |
| 约束 | 技术、法规、预算限制 | **"不能干啥"** |

**三种分析模型**：
- 结构化分析：数据流图(DFD) + 数据字典(DD)
- 面向对象分析：用例图 + 类图 + 活动图（UML）
- 记忆：**"结构画流图，对象画UML"**

---

### 6.6 软件测试速记

**测试的分类口诀**：「**单集系验**」

| 级别 | 对象 | 谁测 | 目标 |
|------|------|------|------|
| **单**元测试 | 单个函数/模块 | 开发人员 | 代码逻辑正确 |
| **集**成测试 | 模块间接口 | 开发/测试 | 模块协作正确 |
| **系**统测试 | 整个系统 | 测试团队 | 满足需求规格 |
| **验**收测试 | 整个系统 | 用户/客户 | 符合用户期望 |

**测试方法**：
| 方法 | 别名 | 特点 | 记忆 |
|------|------|------|------|
| 黑盒测试 | 功能测试 | 不看内部，只看输入输出 | **"管他里面咋写"** |
| 白盒测试 | 结构测试 | 检查代码逻辑路径 | **"透视代码"** |
| 灰盒测试 | 两者结合 | 知道部分内部 | **"半透明"** |

**黑盒测试方法**：
- 等价类划分：把输入分成有效/无效等价类
- 边界值分析：测试边界上的值（最容易出错！）
- 记忆：**"边界最容易出bug"**

**白盒测试覆盖标准**（从弱到强）「**语句→判定→条件→路径**」

---

### 6.7 详细设计速记

**结构化设计 vs 面向对象设计**：
| | 结构化 | 面向对象 |
|---|--------|---------|
| 核心思想 | 功能分解（自顶向下） | 对象+消息 |
| 设计工具 | 结构图、流程图 | UML类图、时序图 |
| 耦合/内聚 | 低耦合、高内聚 | 低耦合、高内聚 |
| 记忆 | **"按功能分块"** | **"按对象分块"** |

**内聚**（从低到高）：偶然<逻辑<时间<过程<通信<顺序<功能
- 记忆：**"越高越好，功能内聚最好"**

**耦合**（从低到高）：无耦合<数据耦合<控制耦合<公共耦合<内容耦合
- 记忆：**"越低越好，数据耦合最理想"**

### 6.9 高频易错点

1. **瀑布模型不能回溯**，需求定了就不能改（这是缺点！）
2. **敏捷≠没文档**，是"刚好够用的文档"
3. **边界值测试比等价类更重要**（边界最容易出bug）
4. **黑盒测试不需要看源码**，白盒测试需要
5. **高内聚低耦合**是设计黄金法则（内聚要高，耦合要低）
6. **验收测试由用户做**，不是开发团队自己做

## 章节：1.1 系统与系统工程笔记

软件工程基础 - 1.1 系统与系统工程 详细笔记

一、系统的基本概念

1.1 什么是系统

系统的定义：
- 系统是由相互作用、相互依赖的若干组成部分结合而成的，具有特定功能的有机整体。
- 系统一词来源于古希腊语"systema"，意为"由部分组成的整体"。

系统的例子：
- 自然界：太阳系、生态系统、人体
- 工程领域：计算机系统、交通系统、电力系统
- 社会领域：教育系统、医疗系统、经济系统
- 软件领域：软件系统、信息系统

1.2 系统的特性

1. 整体性（Integrity）
   - 系统是一个有机整体，不是各个部分的简单相加
   - 整体功能大于部分功能之和（1 + 1 > 2）
   - 例子：一辆汽车由成千上万个零件组成，但单独的零件不能实现汽车的功能，只有组装在一起才能行驶

2. 相关性（Relativity）
   - 系统的各个组成部分之间是相互联系、相互作用的
   - 一个部分的变化会影响其他部分
   - 例子：计算机系统中，CPU、内存、硬盘之间相互配合，一个部件的性能会影响整体性能

3. 目的性（Purposefulness）
   - 任何系统都有明确的目的或目标
   - 系统的各个组成部分都是为了实现这个目标
   - 例子：教育系统的目的是培养人才，医疗系统的目的是治疗疾病

4. 层次性（Hierarchy）
   - 系统可以分为多个层次
   - 每个层次都有自己的系统，同时又是更大系统的一部分
   - 例子：
     - 计算机系统：硬件系统 → 软件系统 → 应用系统
     - 硬件系统：CPU → 内存 → 硬盘 → 输入输出设备
     - CPU：运算器 → 控制器 → 寄存器

5. 环境适应性（Environment Adaptability）
   - 系统存在于一定的环境中
   - 系统需要与环境进行物质、能量、信息的交换
   - 系统需要适应环境的变化
   - 例子：软件系统需要适应硬件的更新、操作系统的升级

1.3 系统的分类

按自然属性分类：
1. 自然系统（Natural System）
   - 由自然物组成的系统
   - 例子：太阳系、生态系统、人体系统
2. 人工系统（Artificial System）
   - 由人类创造的系统
   - 例子：计算机系统、交通系统、软件系统
3. 复合系统（Composite System）
   - 自然系统和人工系统结合的系统
   - 例子：农业系统、水利系统

按物质属性分类：
1. 实体系统（Physical System）
   - 由物质实体组成的系统
   - 例子：机械系统、电气系统
2. 概念系统（Conceptual System）
   - 由概念、原理、方法、制度等组成的系统
   - 例子：知识系统、法律系统、软件系统

按与环境的关系分类：
1. 开放系统（Open System）
   - 与环境有物质、能量、信息交换的系统
   - 例子：大多数系统都是开放系统
2. 封闭系统（Closed System）
   - 与环境没有物质、能量、信息交换的系统
   - 绝对的封闭系统很少见

按状态分类：
1. 静态系统（Static System）
   - 状态不随时间变化的系统
   - 例子：建筑物、地图
2. 动态系统（Dynamic System）
   - 状态随时间变化的系统
   - 例子：计算机系统、交通系统

二、系统工程概述

2.1 什么是系统工程

系统工程的定义：
- 系统工程是一门组织管理系统的规划、研究、设计、制造、试验和使用的科学方法。
- 系统工程是一种对所有系统都具有普遍意义的方法。
- 系统工程是以系统为研究对象，以达到总体最优为目标的一门综合性工程技术。

系统工程的起源：
- 20世纪40年代，美国贝尔电话公司在发展电话通信网络时，首先使用了"系统工程"一词。
- 20世纪60年代，美国阿波罗登月计划成功应用了系统工程方法。
- 20世纪70年代以后，系统工程在世界范围内得到广泛应用。

2.2 系统工程的特点

1. 整体性（整体最优）
   - 不是追求单个部分的最优，而是追求整体的最优
   - 有时为了整体最优，可能需要牺牲部分的利益
   - 例子：在计算机系统设计中，不是追求CPU性能最高，而是追求CPU、内存、硬盘等部件的最佳搭配

2. 综合性（多学科交叉）
   - 系统工程需要综合运用多学科的知识和技术
   - 例子：软件工程需要计算机科学、数学、管理学、心理学等多学科知识

3. 科学性与艺术性相结合
   - 系统工程有科学的方法和工具
   - 同时也需要经验、直觉和创造力
   - 例子：软件架构设计既有科学的原则，也有艺术的成分

4. 目的性
   - 系统工程始终围绕系统的目标进行
   - 所有活动都是为了实现系统的目标

5. 动态性
   - 系统工程考虑系统的动态变化
   - 考虑系统的发展和演化

2.3 系统工程的原则

1. 整体性原则
   - 从整体出发考虑问题
   - 局部服从整体
   - 追求整体最优

2. 综合性原则
   - 综合考虑各方面因素
   - 综合运用各学科知识
   - 综合考虑技术、经济、社会等因素

3. 目的性原则
   - 明确系统的目标
   - 所有活动都围绕目标进行
   - 目标要具体、可测量、可实现

4. 相关性原则
   - 考虑系统各部分之间的关系
   - 考虑系统与环境的关系
   - 协调各部分之间的关系

5. 环境适应性原则
   - 考虑环境的要求和约束
   - 系统要能适应环境的变化
   - 系统要能对环境产生积极影响

6. 创新原则
   - 采用新思想、新技术、新方法
   - 不断改进和优化
   - 保持竞争力

三、系统工程的方法和步骤

3.1 系统工程的方法

霍尔三维结构（Hall Three-Dimensional Structure）：
- 由美国系统工程专家A.D. Hall提出
- 三个维度：
  1. 时间维（Time Dimension）：系统工程的工作阶段
  2. 逻辑维（Logic Dimension）：每个阶段的思维过程
  3. 知识维（Knowledge Dimension）：所需的专业知识

时间维的七个阶段：
1. 规划阶段（Planning）
2. 拟定方案阶段（Programming）
3. 研制阶段（Development）
4. 生产阶段（Production）
5. 安装阶段（Installation）
6. 运行阶段（Operation）
7. 更新阶段（Retirement）

逻辑维的七个步骤：
1. 摆明问题（Problem Definition）
2. 确定目标（Value System Design）
3. 系统综合（System Synthesis）
4. 系统分析（System Analysis）
5. 优化选择（Optimization）
6. 决策（Decision Making）
7. 实施计划（Planning for Action）

知识维的专业知识：
- 工程
- 医学
- 建筑
- 商业
- 法律
- 管理
- 社会科学
- 艺术

3.2 系统工程的一般步骤

1. 问题定义（Problem Definition）
   - 明确要解决的问题
   - 了解问题的背景
   - 确定问题的边界
   - 明确利益相关者

2. 目标确定（Goal Setting）
   - 确定系统的总体目标
   - 将目标分解为具体的子目标
   - 确定目标的优先级
   - 建立评价指标体系

3. 方案设计（Solution Design）
   - 收集相关信息
   - 进行系统分析
   - 提出多个备选方案
   - 每个方案都要满足目标要求

4. 方案评价（Solution Evaluation）
   - 建立评价标准
   - 对每个方案进行评价
   - 比较各个方案的优缺点
   - 考虑技术、经济、社会等因素

5. 方案选择（Solution Selection）
   - 根据评价结果选择最优方案
   - 考虑风险和不确定性
   - 获得利益相关者的认可

6. 方案实施（Solution Implementation）
   - 制定详细的实施计划
   - 组织实施
   - 监控实施过程
   - 解决实施中的问题

7. 系统评价（System Evaluation）
   - 评价系统的实际效果
   - 与预期目标进行比较
   - 总结经验教训
   - 提出改进建议

8. 系统维护（System Maintenance）
   - 系统的日常维护
   - 系统的更新和升级
   - 适应环境的变化
   - 持续改进

四、系统分析

4.1 什么是系统分析

系统分析的定义：
- 系统分析是系统工程的重要组成部分
- 系统分析是在明确系统目标的前提下，分析和研究系统的各个组成部分及其相互关系，以及系统与环境之间的关系，为系统设计提供依据。

系统分析的目的：
- 了解系统的现状
- 发现系统存在的问题
- 明确系统的需求
- 为系统设计提供基础

4.2 系统分析的内容

1. 系统目标分析
   - 明确系统的总体目标
   - 分析目标的合理性
   - 分解目标为子目标
   - 分析目标之间的关系

2. 系统结构分析
   - 分析系统的组成部分
   - 分析各部分之间的关系
   - 分析系统的层次结构
   - 建立系统的结构模型

3. 系统功能分析
   - 分析系统的功能
   - 分析功能之间的关系
   - 建立功能模型
   - 分析功能的合理性

4. 系统环境分析
   - 分析系统的外部环境
   - 分析环境对系统的影响
   - 分析系统对环境的影响
   - 分析环境的变化趋势

5. 系统需求分析
   - 明确用户的需求
   - 分析需求的优先级
   - 建立需求模型
   - 验证需求的完整性和一致性

4.3 系统分析的方法

1. 结构化分析方法（SA，Structured Analysis）
   - 自顶向下，逐步分解
   - 使用数据流图（DFD，Data Flow Diagram）
   - 使用数据字典（DD，Data Dictionary）
   - 使用判定树和判定表

2. 面向对象分析方法（OOA，Object-Oriented Analysis）
   - 识别对象和类
   - 分析对象之间的关系
   - 使用UML建模
   - 使用用例图、类图、时序图等

3. 系统动力学方法
   - 建立系统的动态模型
   - 分析系统的反馈机制
   - 模拟系统的行为
   - 预测系统的发展趋势

五、系统设计

5.1 什么是系统设计

系统设计的定义：
- 系统设计是根据系统分析的结果，设计系统的结构和实现方案
- 系统设计是从"做什么"到"怎么做"的过程

系统设计的目标：
- 满足系统的功能需求
- 满足系统的非功能需求（性能、可靠性、可维护性等）
- 技术先进
- 经济合理
- 易于实现
- 易于维护

5.2 系统设计的原则

1. 模块化原则（Modularity）
   - 将系统划分为多个模块
   - 每个模块有独立的功能
   - 模块之间有明确的接口
   - 高内聚，低耦合

2. 抽象原则（Abstraction）
   - 忽略细节，关注本质
   - 分层抽象
   - 使用抽象数据类型

3. 信息隐蔽原则（Information Hiding）
   - 隐藏模块的内部实现细节
   - 只通过接口与外部交互
   - 减少模块之间的依赖

4. 逐步求精原则（Stepwise Refinement）
   - 自顶向下，逐步细化
   - 先设计高层，再设计低层
   - 先设计总体，再设计细节

5. 一致性原则（Consistency）
   - 设计风格一致
   - 命名一致
   - 接口一致
   - 文档一致

6. 可扩展性原则（Scalability）
   - 考虑系统的扩展需求
   - 预留扩展接口
   - 设计灵活的架构

7. 可靠性原则（Reliability）
   - 设计健壮的系统
   - 考虑异常情况
   - 有容错机制
   - 有备份和恢复机制

5.3 系统设计的内容

1. 架构设计（Architecture Design）
   - 设计系统的总体架构
   - 选择架构模式
   - 划分系统的层次
   - 确定系统的组件

2. 模块设计（Module Design）
   - 设计系统的模块
   - 确定模块的功能
   - 设计模块的接口
   - 设计模块的内部结构

3. 数据设计（Data Design）
   - 设计数据结构
   - 设计数据库
   - 设计数据的存储方式
   - 设计数据的访问方式

4. 接口设计（Interface Design）
   - 设计模块之间的接口
   - 设计系统与外部的接口
   - 设计用户界面
   - 设计接口的协议

5. 过程设计（Process Design）
   - 设计系统的处理流程
   - 设计算法
   - 设计控制流程
   - 设计异常处理

六、系统工程在软件工程中的应用

6.1 软件工程与系统工程的关系

软件工程是系统工程的一个分支：
- 软件工程是系统工程在软件领域的应用
- 软件工程借鉴了系统工程的思想和方法
- 软件工程有自己的特点和方法

软件工程的系统观：
- 将软件看作一个系统
- 考虑软件与硬件的关系
- 考虑软件与用户的关系
- 考虑软件与环境的关系

6.2 软件工程的系统工程方法

软件开发生命周期（SDLC）：
- 可行性研究
- 需求分析
- 系统设计
- 编码
- 测试
- 部署
- 维护

这与系统工程的步骤是一致的。

七、总结

7.1 系统的要点

- 系统可以从不同角度分类

7.2 系统工程的要点
- 系统工程是组织管理系统的科学方法
- 系统工程追求整体最优
- 系统工程有科学的方法和步骤
- 霍尔三维结构是系统工程的重要方法

7.3 系统工程在软件工程中的应用
- 软件工程是系统工程的一个分支
- 软件工程借鉴了系统工程的思想和方法
- 用系统工程的方法指导软件开发

7.4 学习系统工程的意义
- 建立系统思维
- 掌握系统工程的方法

## 章节：1.2 软件工程概述笔记

软件工程基础 - 1.2 软件工程概述 详细笔记

一、软件危机

1.1 什么是软件危机

软件危机（Software Crisis）的定义：
- 软件危机是指在计算机软件开发和维护过程中遇到的一系列严重问题
- 这些问题导致：
  - 软件项目延期
  - 软件项目超支
  - 软件质量低下
  - 软件难以维护
  - 软件不可靠

软件危机的历史：
- 20世纪60年代开始出现
- 随着软件规模越来越大，问题越来越严重
- 1968年，NATO（北大西洋公约组织）在德国召开了第一次软件工程会议
- 这次会议正式提出了"软件工程"的概念

1.2 软件危机的表现

软件危机的主要表现：

1. 软件项目延期
   - 项目不能按时交付
   - 延期几个月甚至几年很常见
   - 例子：
     - IBM的OS/360：延期数年
     - Windows Vista：延期多次

2. 软件项目超支
   - 项目成本超过预算
   - 超支几倍很常见
   - 例子：
     - 美国政府的一些IT项目：超支数亿美元

3. 软件质量低下
   - 软件有很多bug
   - 软件不可靠
   - 软件经常崩溃
   - 例子：
     - Therac-25医疗设备：软件bug导致患者死亡
     - 航天飞机：软件问题导致任务失败

4. 软件难以维护
   - 软件难以理解
   - 软件难以修改
   - 修改软件容易引入新bug
   - 维护成本高
   - 例子：
     - 遗留系统（Legacy System）：维护成本是开发成本的几倍

5. 软件不可移植
   - 软件只能在特定的硬件/操作系统上运行
   - 移植到其他平台很困难
   - 例子：
     - 早期的软件：与特定硬件紧密绑定

6. 软件用户不满意
   - 软件不能满足用户需求
   - 软件功能不符合用户期望
   - 软件易用性差
   - 例子：
     - 很多企业软件：用户体验差

1.3 软件危机的原因

软件危机的原因：

1. 软件的复杂性
   - 软件逻辑复杂
   - 软件规模大
   - 软件需求多变
   - 软件难以可视化

2. 软件开发和维护的方法不当
   - 忽视需求分析
   - 轻视软件维护
   - 没有规范的开发流程
   - 缺乏有效的项目管理

3. 软件成本高
   - 软件开发需要大量人力
   - 软件维护成本高
   - 软件测试成本高

4. 软件进度难以控制
   - 软件进度难以估计
   - 软件开发过程中需求变化
   - 软件难以量化

5. 软件质量保证困难
   - 软件测试不能穷尽所有情况
   - 软件质量难以保证
   - 软件可靠性难以评估

1.4 软件危机的解决

解决软件危机的途径：

1. 技术措施
   - 研究更好的软件开发方法
   - 使用更好的软件开发工具
   - 使用更好的软件开发环境
   - 研究软件复用技术

2. 管理措施
   - 加强软件项目管理
   - 加强软件质量管理
   - 加强软件配置管理
   - 加强人员培训

3. 法律措施
   - 制定软件相关的法律
   - 保护软件知识产权
   - 规范软件市场

这就引出了软件工程。

二、软件工程的定义

2.1 什么是软件工程

软件工程（Software Engineering）的定义：
- 1968年NATO会议提出
- Fritz Bauer的定义：
  "软件工程是建立和使用一套合理的工程原则，以便获得经济的软件，这些软件是可靠的，可以在实际机器上高效地运行。"
- IEEE的定义：
  "软件工程是：
  1. 将系统化的、规范的、可度量的方法应用于软件的开发、运行和维护，即将工程化应用于软件。
  2. 对上述方法的研究。"

软件工程的核心思想：
- 将工程化的方法应用于软件开发
- 使用系统化的方法
- 遵循规范的流程
- 可度量的过程

2.2 软件工程的目标

软件工程的目标：
1. 低成本：开发和维护软件的成本低
2. 按时交付：软件项目按时完成
3. 高质量：软件质量高，可靠、易用、可维护
4. 满足需求：软件满足用户的需求
5. 可维护：软件易于理解、修改和扩展
6. 可移植：软件易于移植到其他平台

这些目标之间有时是冲突的：
- 高质量可能导致高成本
- 快速交付可能导致低质量
- 软件工程需要在这些目标之间权衡

2.3 软件工程的要素

软件工程的三要素：
1. 方法（Methods）：如何做
2. 工具（Tools）：用什么做
3. 过程（Processes）：做的顺序

1. 方法
   - 软件开发的技术方法
   - 包括：
     - 需求分析方法
     - 设计方法
     - 编码方法
     - 测试方法
     - 维护方法
   - 例子：
     - 结构化方法（Structured Method）
     - 面向对象方法（Object-Oriented Method）
     - 敏捷方法（Agile Method）

2. 工具
   - 软件工程的辅助工具
   - 包括：
     - 需求管理工具
     - 设计工具
     - 编码工具（IDE）
     - 测试工具
     - 配置管理工具
     - 项目管理工具
   - 例子：
     - IDE：Eclipse、IntelliJ、Visual Studio
     - 版本控制：Git、SVN
     - 项目管理：Jira、Trello
     - 测试：JUnit、Selenium

3. 过程
   - 软件工程的工作流程
   - 定义了：
     - 做什么
     - 什么时候做
     - 谁来做
     - 怎么做
   - 例子：
     - 瀑布模型（Waterfall）
     - 增量模型（Incremental）
     - 螺旋模型（Spiral）
     - 敏捷过程（Agile）

三、软件工程的内容

3.1 软件工程的研究内容

软件工程的研究内容：
1. 软件需求工程
2. 软件设计
3. 软件编码
4. 软件测试
5. 软件维护
6. 软件项目管理
7. 软件质量管理
8. 软件配置管理
9. 软件工程环境
10. 软件复用

3.2 软件过程

软件过程（Software Process）的定义：
- 软件过程是开发软件所需的一系列活动的集合
- 软件过程定义了：
  - 活动（Activities）：做什么
  - 角色（Roles）：谁来做
  - 工件（Artifacts）：产生什么
  - 顺序（Sequence）：什么时候做

软件过程的重要性：
- 提高软件质量
- 提高开发效率
- 降低开发成本
- 便于项目管理
- 便于经验积累

常见的软件过程模型：
1. 瀑布模型（Waterfall Model）
2. 增量模型（Incremental Model）
3. 原型模型（Prototype Model）
4. 螺旋模型（Spiral Model）
5. 敏捷过程（Agile Process）
6. Rational统一过程（Rational Unified Process，RUP）

3.3 软件生命周期

软件生命周期（Software Life Cycle）的定义：
- 软件生命周期是软件从概念到退役的整个过程
- 通常包括：
  1. 可行性研究
  2. 需求分析
  3. 软件设计
  4. 编码
  5. 测试
  6. 部署
  7. 维护
  8. 退役

软件生命周期阶段：

1. 可行性研究
   - 研究项目是否可行
   - 包括：
     - 技术可行性
     - 经济可行性
     - 操作可行性
   - 输出：可行性研究报告

2. 需求分析
   - 确定用户需求
   - 包括：
     - 功能需求
     - 非功能需求
   - 输出：需求规格说明书（SRS）

3. 软件设计
   - 设计软件的结构
   - 包括：
     - 概要设计（总体设计）
     - 详细设计
   - 输出：设计文档

4. 编码
   - 将设计转换为代码
   - 选择编程语言
   - 遵循编码规范
   - 输出：源代码

5. 测试
   - 发现软件中的bug
   - 包括：
     - 单元测试
     - 集成测试
     - 系统测试
     - 验收测试
   - 输出：测试报告

6. 部署
   - 将软件部署到生产环境
   - 包括：
     - 安装
     - 配置
     - 培训
   - 输出：运行的软件

7. 维护
   - 修改软件以适应变化
   - 包括：
     - 纠错性维护
     - 适应性维护
     - 完善性维护
     - 预防性维护
   - 维护阶段通常占软件生命周期的大部分时间

8. 退役
   - 软件不再使用
   - 数据迁移
   - 文档归档

四、软件工程的原则

4.1 软件工程的基本原则

软件工程的基本原则：
1. 抽象（Abstraction）
2. 模块化（Modularity）
3. 信息隐藏（Information Hiding）
4. 局部化（Localization）
5. 一致性（Consistency）
6. 完整性（Completeness）
7. 可验证性（Verifiability）

1. 抽象
   - 忽略不重要的细节
   - 关注重要的特征
   - 例子：
     - 函数：隐藏实现细节，只暴露接口
     - 类：隐藏私有成员，只暴露公有成员
     - 模块：隐藏内部实现，只暴露接口

2. 模块化
   - 将软件分解为独立的模块
   - 每个模块有明确的职责
   - 模块之间通过接口交互
   - 好处：
     - 易于理解
     - 易于开发
     - 易于测试
     - 易于维护
     - 易于复用

3. 信息隐藏
   - 隐藏模块的内部实现细节
   - 只暴露必要的接口
   - 好处：
     - 减少模块之间的依赖
     - 修改一个模块不会影响其他模块
     - 提高可维护性

4. 局部化
   - 相关的元素放在一起
   - 高内聚（High Cohesion）：一个模块只做一件事
   - 低耦合（Low Coupling）：模块之间的依赖少
   - 好处：
     - 易于理解
     - 易于修改

5. 一致性
   - 软件的各个部分风格一致
   - 包括：
     - 命名一致
     - 格式一致
     - 接口一致
     - 设计一致
   - 好处：
     - 易于理解
     - 易于使用

6. 完整性
   - 软件满足所有需求
   - 不遗漏功能
   - 不遗漏边界条件
   - 好处：
     - 满足用户需求
     - 提高软件质量

7. 可验证性
   - 软件易于测试
   - 易于验证软件的正确性
   - 好处：
     - 提高软件质量
     - 降低测试成本

4.2 软件工程的实践原则

软件工程的实践原则：
1. 先想后做（Think Before You Code）
   - 先设计，后编码
   - 不要急于编码

2. 分而治之（Divide and Conquer）
   - 将大问题分解为小问题
   - 逐个解决小问题

3. 迭代开发（Iterative Development）
   - 不要试图一次完成所有功能
   - 先完成核心功能，然后迭代完善

4. 持续测试（Continuous Testing）
   - 不要等到最后才测试
   - 边开发边测试

5. 复用（Reuse）
   - 不要重复发明轮子
   - 复用现有的代码、库、框架

6. 文档（Documentation）
   - 编写必要的文档
   - 不要过度文档，也不要不文档

7. 沟通（Communication）
   - 与用户沟通
   - 与团队成员沟通
   - 沟通是项目成功的关键

## 章节：1.3 可信软件笔记

软件工程基础 - 1.3 可信软件 详细笔记

一、可信软件概述

1.1 什么是可信软件

可信软件（Trustworthy Software）的定义：
- 可信软件是指可以被用户信任的软件
- 它在预定的时间内和预定的条件下，能够完成预定的功能
- 可信软件具有多个属性，包括：
  - 可靠性（Reliability）
  - 可用性（Availability）
  - 安全性（Security）
  - 可维护性（Maintainability）
  - 性能（Performance）

可信的重要性：
- 软件已经渗透到生活的方方面面
- 关键领域的软件故障会造成严重后果
  - 医疗设备：可能导致患者死亡
  - 航空航天：可能导致事故
  - 金融系统：可能导致经济损失
  - 交通系统：可能导致事故
- 可信软件是社会对软件的基本要求

1.2 可信软件的发展

早期软件（1950s-1960s）：
- 软件规模小
- 对可信性要求不高
- 主要关注功能

软件危机时期（1960s-1970s）：
- 软件规模越来越大
- 软件质量问题突出
- 开始关注软件质量

软件工程时期（1970s至今）：
- 软件工程提出
- 开始系统地研究软件质量
- 提出了各种质量模型和标准

现代可信软件（2000s至今）：
- 互联网和移动互联网的普及
- 软件安全问题突出
- 可信性成为软件的重要指标
- 研究方向：
  - 软件可靠性工程
  - 软件安全性工程
  - 软件验证和确认
  - 软件容错

二、可信软件的属性

2.1 可靠性

可靠性（Reliability）的定义：
- 可靠性是软件在规定的条件下和规定的时间内，完成规定功能的能力
- 可靠性的定量指标：
  - 平均无故障时间（Mean Time Between Failures，MTBF）
  - 故障概率（Failure Probability）

可靠性的度量：
1. MTBF（Mean Time Between Failures）：
   - 平均无故障时间
   - 两次故障之间的平均时间
   - MTBF越大，可靠性越高

2. MTTF（Mean Time To Failure）：
   - 平均失效时间
   - 从开始运行到第一次失效的平均时间
   - 对于不可修复的系统，MTTF = MTBF

3. MTTR（Mean Time To Repair）：
   - 平均修复时间
   - 修复故障的平均时间
   - MTTR越小，可用性越高

4. 可靠性函数R(t)：
   - 系统在时间t内不失效的概率
   - R(0) = 1
   - R(t)随t增大而减小

5. 故障率函数λ(t)：
   - 瞬时故障率
   - 在时刻t，单位时间内发生故障的概率
   - 浴盆曲线（Bathtub Curve）：
     - 早期故障期：故障率高，逐渐降低
     - 偶然故障期：故障率低，恒定
     - 耗损故障期：故障率高，逐渐升高

提高可靠性的方法：
1. 容错（Fault Tolerance）：
   - 即使有故障，系统也能继续运行
   - 方法：
     - 冗余（Redundancy）
     - 恢复（Recovery）
     - 表决（Voting）

2. 避错（Fault Avoidance）：
   - 避免故障的发生
   - 方法：
     - 好的设计
     - 代码审查
     - 测试

3. 查错（Fault Detection）：
   - 及时发现故障
   - 方法：
     - 检查点（Checkpoints）
     - 断言（Assertions）
     - 日志（Logging）

2.2 可用性

可用性（Availability）的定义：
- 可用性是软件在需要时能够正常使用的能力
- 可用性的定量指标：
  - 可用性 = MTBF / (MTBF + MTTR)
  - 通常用"9"表示：
    - 99%：每年停机约3.65天
    - 99.9%：每年停机约8.76小时
    - 99.99%：每年停机约52.56分钟
    - 99.999%：每年停机约5.26分钟

提高可用性的方法：
1. 冗余（Redundancy）：
   - 硬件冗余：多个相同的部件
   - 软件冗余：多个版本的软件
   - 信息冗余：校验码、纠错码
   - 时间冗余：重复执行

2. 故障检测和恢复：
   - 快速检测故障
   - 快速恢复
   - 自动切换

3. 维护：
   - 预防性维护
   - 快速修复

2.3 安全性

安全性（Security）的定义：
- 安全性是软件保护信息和资源，防止未授权访问、使用、披露、破坏、修改的能力
- 安全性的三个基本要素（CIA）：
  1. 机密性（Confidentiality）：信息不被未授权访问
  2. 完整性（Integrity）：信息不被未授权修改
  3. 可用性（Availability）：信息和资源在需要时可用

安全威胁：
1. 窃听（Eavesdropping）：未授权获取信息
2. 篡改（Tampering）：未授权修改信息
3. 伪造（Spoofing）：冒充他人
4. 否认（Repudiation）：否认自己的行为
5. 拒绝服务（Denial of Service，DoS）：使系统不可用
6. 特权提升（Privilege Escalation）：获取更高的权限

安全机制：
1. 认证（Authentication）：确认身份
   - 密码
   - 令牌
   - 生物特征
   - 双因素认证

2. 授权（Authorization）：控制权限
   - 访问控制列表（ACL）
   - 角色-based访问控制（RBAC）

3. 加密（Encryption）：保护信息机密性
   - 对称加密：DES、AES
   - 非对称加密：RSA、ECC

4. 完整性保护：
   - 哈希函数：SHA-1、SHA-256
   - 消息认证码（MAC）
   - 数字签名

5. 审计（Auditing）：记录行为
   - 日志
   - 监控

2.4 可维护性

可维护性（Maintainability）的定义：
- 可维护性是软件能够被理解、修改、适应新环境的能力
- 可维护性包括：
  1. 可理解性（Understandability）：软件容易理解
  2. 可修改性（Modifiability）：软件容易修改
  3. 可测试性（Testability）：软件容易测试
  4. 可移植性（Portability）：软件容易移植到新环境

提高可维护性的方法：
1. 好的设计：
   - 模块化
   - 高内聚低耦合
   - 清晰的接口

2. 好的编码：
   - 清晰的代码
   - 有意义的命名
   - 适当的注释
   - 遵循编码规范

3. 好的文档：
   - 需求文档
   - 设计文档
   - 用户手册
   - 维护手册

4. 配置管理：
   - 版本控制
   - 变更管理
   - 发布管理

2.5 性能

性能（Performance）的定义：
- 性能是软件在时间和空间上的效率
- 性能的指标：
  1. 响应时间（Response Time）：系统对请求的响应时间
  2. 吞吐量（Throughput）：单位时间内处理的请求数
  3. 资源利用率（Resource Utilization）：CPU、内存、网络的利用率
  4. 并发数（Concurrency）：同时处理的请求数

提高性能的方法：
1. 算法优化：
   - 选择更好的算法
   - 降低时间复杂度
   - 降低空间复杂度

2. 数据结构优化：
   - 选择合适的数据结构
   - 优化数据访问

3. 缓存（Caching）：
   - 缓存频繁访问的数据
   - 减少数据库访问
   - 减少网络访问

4. 并发（Concurrency）：
   - 多线程
   - 异步处理
   - 连接池

5. 负载均衡（Load Balancing）：
   - 将负载分布到多个服务器
   - 提高吞吐量
   - 提高可用性

三、可信软件的开发

可信软件的开发过程：

  - 现场测试

3.3 软件可靠性工程

软件可靠性工程（Software Reliability Engineering，SRE）：

# 1.4 软件工程的研究对象与基本原理笔记

## 一、软件工程的研究对象
### 1.1 软件的本质特性
软件是计算机系统中与硬件相互依存的另一部分，它包括程序、数据及其相关文档的完整集合。

**软件的特性**：
1. **抽象性**：软件是逻辑实体，不是物理实体
2. **复杂性**：软件的复杂性随规模呈指数增长
3. **一致性**：软件必须严格按照规格说明执行
4. **可变性**：软件需要不断修改和演化
5. **不可见性**：软件的代码和结构不可直接观察

### 1.2 软件工程的研究内容
1. **软件过程**：软件开发、维护和管理的过程
2. **软件方法**：软件开发的技术和方法
3. **软件工具**：支持软件开发的工具和环境
4. **软件管理**：软件项目的计划、组织、控制

6. **软件维护**：软件的修改、更新和演化

## 二、软件工程的基本原理
### 2.1 软件工程的基本目标
1. **正确性**：软件满足规格说明
2. **可靠性**：软件在规定条件下无故障运行
3. **可用性**：软件易于学习和使用
4. **效率**：软件资源消耗少、响应快
5. **可维护性**：软件易于修改和扩展
6. **可移植性**：软件易于从一个环境移植到另一个环境

### 2.2 软件工程的七条基本原理（Boehm）
1. **用分阶段的生命周期计划严格管理**
   - 将软件生命周期划分为多个阶段
   - 每个阶段都有明确的任务和目标
   - 制定详细的计划并严格执行

2. **坚持进行阶段评审**
   - 每个阶段结束时进行评审
   - 及早发现和纠正错误
   - 避免错误传递到下一阶段

3. **实行严格的产品控制**
   - 建立基线（Baseline）
   - 控制变更，避免混乱
   - 配置管理

4. **采用现代程序设计技术**
   - 结构化分析与设计
   - 面向对象方法
   - 模块化设计

5. **结果应能清楚地审查**
   - 文档完整、规范
   - 代码清晰、可读
   - 便于评审和测试

6. **开发小组的人员应该少而精**
   - 小型、高效的团队
   - 良好的沟通和协作
   - 人员素质比数量更重要

7. **承认不断改进软件工程实践的必要性**
   - 持续学习和改进
   - 采用新技术和新方法
   - 总结经验教训

### 2.3 软件工程的原则（补充）
1. **抽象**：抽取事物的本质特性，忽略非本质细节
2. **信息隐藏**：将模块的内部信息隐藏起来，只暴露必要的接口
3. **模块化**：将软件分解为独立的模块
4. **局部化**：相关的逻辑和数据放在一起
5. **一致性**：使用统一的概念、符号和格式
6. **完整性**：软件系统的各个部分完整无缺
7. **可验证性**：系统的各个部分易于测试和验证

## 章节：2.2 软件工程经典生存周期模型笔记

# 2.2 软件工程经典生存周期模型笔记

## 一、软件过程模型概述
### 1.1 软件过程模型的概念
软件过程模型（Software Process Model）是软件生命周期过程的抽象表示，它规定了软件过程的活动、活动之间的顺序和关系。

### 1.2 过程模型的作用
1. **指导开发**：为软件开发提供指导
2. **管理项目**：帮助管理软件项目
3. **提高质量**：有助于提高软件质量
4. **降低风险**：降低开发风险
5. **沟通工具**：作为项目成员之间的沟通工具

## 二、瀑布模型（Waterfall Model）
### 2.1 瀑布模型的提出
瀑布模型由Winston Royce于1970年提出，是最早的软件过程模型之一。

### 2.2 瀑布模型的阶段
1. **可行性研究**
   - 技术可行性
   - 经济可行性
   - 操作可行性

2. **需求分析**
   - 需求获取
   - 需求分析
   - 需求规格说明
   - 需求验证

3. **系统设计**
   - 概要设计
   - 详细设计

4. **编码**
   - 编写代码
   - 单元测试

5. **测试**
   - 集成测试
   - 系统测试
   - 验收测试

6. **运行与维护**
   - 部署
   - 运行
   - 维护

### 2.3 瀑布模型的特点
1. **线性顺序**：各阶段按顺序进行
2. **阶段间有明确界限**：前一阶段完成后才能进入下一阶段
3. **文档驱动**：每个阶段都有明确的文档产出
4. **强调验证**：每个阶段结束时进行评审和验证

### 2.4 瀑布模型的优点
1. **简单直观**：模型简单，易于理解和掌握
2. **文档完善**：每个阶段都有详细的文档
3. **易于管理**：线性流程，易于项目管理
4. **强调质量**：每个阶段都有验证活动

### 2.5 瀑布模型的缺点
1. **不适应变化**：难以适应需求变化
2. **风险高**：后期才能看到软件
3. **用户参与少**：用户参与度低
4. **阻塞状态**：开发人员可能处于等待状态
5. **文档工作量大**：需要编写大量文档

### 2.6 瀑布模型的适用范围
1. **需求明确且稳定**
2. **技术成熟**
3. **项目规模较小**
4. **类似项目经验丰富**

## 三、增量模型（Incremental Model）
### 3.1 增量模型的基本思想
增量模型将软件产品作为一系列增量来开发，每个增量都是一个可交付的产品。

### 3.2 增量模型的过程
1. **第一个增量**：核心功能
2. **第二个增量**：增加新功能
3. **第三个增量**：继续增加功能
4. ...
5. **最后一个增量**：完成所有功能

### 3.3 增量模型的特点
1. **分批交付**：分批向用户交付软件
2. **早期反馈**：早期获得用户反馈
3. **降低风险**：降低开发风险
4. **灵活适应**：可以适应需求变化

### 3.4 增量模型的优点
1. **早期交付**：早期交付部分功能
2. **用户反馈**：获得早期用户反馈
3. **降低风险**：降低整体风险
4. **灵活适应**：可以适应变化
5. **提高质量**：每个增量都经过测试

### 3.5 增量模型的缺点
1. **架构设计困难**：需要考虑所有增量
2. **增量划分困难**：难以合理划分增量
3. **可能影响性能**：多次集成可能影响性能
4. **需要良好设计**：需要良好的架构设计

### 3.6 增量模型的适用范围
1. **需求可以分阶段实现**
2. **需要早期交付**
3. **市场压力大**
4. **希望降低风险**

## 四、原型模型（Prototype Model）
### 4.1 原型模型的基本思想
快速构建一个原型，让用户试用，根据用户反馈进行改进。

### 4.2 原型模型的类型
1. **探索型原型**
   - 探索需求
   - 明确需求后丢弃

2. **实验型原型**
   - 实验设计方案
   - 验证可行性

3. **演化型原型**
   - 逐步演化
   - 最终成为产品

### 4.3 原型模型的过程
1. **快速构建原型**
2. **用户试用**
3. **收集反馈**
4. **修改原型**
5. **重复2-4**
6. **最终产品**

### 4.4 原型模型的优点
1. **需求明确**：帮助明确需求
2. **用户参与**：用户参与度高
3. **降低风险**：降低需求风险
4. **提高满意度**：提高用户满意度

### 4.5 原型模型的缺点
1. **原型质量问题**：原型可能质量不高
2. **用户期望过高**：用户可能期望过高
3. **难以丢弃**：可能难以丢弃原型
4. **开发效率**：可能影响开发效率

### 4.6 原型模型的适用范围
1. **需求不明确**
2. **用户参与度高**
3. **需要快速验证**
4. **新技术探索**

## 五、螺旋模型（Spiral Model）
### 5.1 螺旋模型的提出
螺旋模型由Barry Boehm于1988年提出，结合了瀑布模型和原型模型的特点，强调风险分析。

### 5.2 螺旋模型的四个象限
1. **制定计划**
   - 确定目标
   - 选择方案
   - 制定计划

2. **风险分析**
   - 识别风险
   - 分析风险
   - 制定对策

3. **实施工程**
   - 开发软件
   - 验证软件

4. **客户评估**
   - 用户评估
   - 提出反馈
   - 计划下一轮

### 5.3 螺旋模型的特点
1. **迭代开发**：多轮迭代
2. **风险驱动**：强调风险分析
3. **结合多种模型**：结合瀑布、原型等模型
4. **灵活适应**：可以适应变化

### 5.4 螺旋模型的优点
1. **风险控制**：强调风险分析
2. **灵活适应**：可以适应变化
3. **用户参与**：用户参与度高
4. **质量保证**：每轮都有验证

### 5.5 螺旋模型的缺点
1. **复杂**：模型复杂，难以理解
2. **管理困难**：项目管理困难
3. **成本高**：开发成本高
4. **周期长**：开发周期长
5. **风险分析依赖经验**：风险分析依赖经验

### 5.6 螺旋模型的适用范围
1. **大型复杂项目**
2. **高风险项目**
3. **需求不确定**
4. **新技术应用**

## 六、喷泉模型（Fountain Model）
### 6.1 喷泉模型的特点
喷泉模型主要用于面向对象开发，特点是：
1. **迭代和无间隙**：各阶段之间没有明显界限
2. **并行开发**：多个阶段可以并行进行
3. **增量开发**：增量式开发
4. **面向对象**：适合面向对象开发

### 6.2 喷泉模型的优点
1. **高效率**：并行开发，效率高
2. **灵活**：灵活适应变化
3. **复用**：支持软件复用
4. **面向对象**：适合面向对象

### 6.3 喷泉模型的缺点
1. **管理困难**：项目管理困难
2. **需要良好设计**：需要良好的架构设计
3. **文档要求高**：文档要求高

## 七、V模型（V-Model）
### 7.1 V模型的特点
V模型是瀑布模型的变种，强调测试与开发的对应关系：
- 单元测试 ↔ 详细设计
- 集成测试 ↔ 概要设计
- 系统测试 ↔ 需求分析
- 验收测试 ↔ 用户需求

### 7.2 V模型的优点
1. **测试明确**：测试活动明确
2. **质量保证**：强调质量保证
3. **易于理解**：模型简单易懂

### 7.3 V模型的缺点
1. **灵活性差**：灵活性差
2. **不适应变化**：不适应变化

## 八、过程模型的选择
### 8.1 选择考虑因素
1. **需求稳定性**
2. **项目规模**
3. **技术成熟度**
4. **风险程度**
5. **用户参与度**
6. **团队经验**

### 8.2 模型选择建议
| 情况 | 推荐模型 |
|------|----------|
| 需求明确稳定 | 瀑布模型 |
| 需求可以分批 | 增量模型 |
| 需求不明确 | 原型模型 |
| 大型高风险 | 螺旋模型 |
| 面向对象 | 喷泉模型 |
| 强调测试 | V模型 |

## 章节：2.3 敏捷软件开发过程笔记

# 2.3 敏捷软件开发过程笔记

## 一、敏捷开发概述
### 1.1 敏捷开发的起源
敏捷开发（Agile Software Development）源于2001年的《敏捷宣言》（Agile Manifesto）。

**敏捷宣言的作者**：17位软件开发思想领袖，包括Kent Beck、Martin Fowler、Robert C. Martin等。

### 1.2 敏捷宣言的四个核心价值
```
个体和互动 高于 流程和工具
可工作的软件 高于 详尽的文档
客户合作 高于 合同谈判
响应变化 高于 遵循计划
```

**解读**：
- 虽然右项也有价值，但我们更重视左项
- 不是否定右项，而是强调左项的重要性

### 1.3 敏捷开发的12个原则
1. **我们最优先要做的是通过尽早的、持续的交付有价值的软件来使客户满意**

2. **即使到了开发的后期，也欢迎改变需求。敏捷过程利用变化来为客户创造竞争优势**

3. **经常性地交付可以工作的软件，交付的间隔可以从几个星期到几个月，交付的时间间隔越短越好**

4. **在整个项目开发期间，业务人员和开发人员必须天天都在一起工作**

5. **围绕被激励起来的个人来构建项目。给他们提供所需要的环境和支持，并且信任他们能够完成工作**

6. **在团队内部，最具有效果并且富有效率的传递信息的方法，就是面对面的交谈**

7. **工作的软件是首要的进度度量标准**

8. **敏捷过程提倡可持续的开发速度。责任人、开发者和用户应该能够保持一个长期的、恒定的开发速度**

9. **不断地关注优秀的技能和好的设计会增强敏捷能力**

10. **简单——使未完成的工作最大化的艺术——是根本的**

11. **最好的架构、需求和设计出自于自组织的团队**

12. **每隔一定时间，团队会在如何才能更有效地工作方面进行反省，然后相应地对自己的行为进行调整**

## 二、敏捷开发方法
### 2.1 Scrum
#### 2.1.1 Scrum概述
Scrum是最流行的敏捷开发方法之一，是一个迭代增量的过程框架。

#### 2.1.2 Scrum的角色
1. **产品负责人（Product Owner）**
   - 负责产品待办列表（Product Backlog）
   - 确定优先级
   - 代表客户利益

2. **Scrum Master**
   - 服务型领导
   - 移除障碍
   - 促进团队协作
   - 确保Scrum规则被遵守

3. **开发团队（Development Team）**
   - 5-9人
   - 自组织
   - 跨职能
   - 负责交付可工作的产品增量

#### 2.1.3 Scrum的事件
1. **Sprint（冲刺）**
   - 时间盒：通常2-4周
   - 目标不变
   - 交付可工作的产品增量

2. **Sprint规划会议（Sprint Planning）**
   - 确定Sprint目标
   - 选择产品待办列表项
   - 分解为任务

3. **每日站会（Daily Scrum）**
   - 15分钟时间盒
   - 三个问题：
     * 昨天完成了什么
     * 今天计划做什么
     * 遇到了什么障碍

4. **Sprint评审（Sprint Review）**
   - 演示产品增量
   - 收集反馈
   - 调整产品待办列表

5. **Sprint回顾（Sprint Retrospective）**
   - 回顾过程
   - 识别改进点
   - 制定改进计划

#### 2.1.4 Scrum的工件
1. **产品待办列表（Product Backlog）**
   - 产品需求的有序列表
   - 优先级排序
   - 持续细化

2. **Sprint待办列表（Sprint Backlog）**
   - 选定的产品待办列表项
   - 分解的任务
   - 团队的工作计划

3. **产品增量（Increment）**
   - 可工作的产品
   - 满足完成的定义（DoD）
   - 潜在可发布

#### 2.1.5 完成的定义（Definition of Done）
DoD是质量标准，确保增量的质量：
- 代码完成
- 代码审查
- 单元测试通过
- 集成测试通过
- 文档完成
- 用户验收测试通过

### 2.2 极限编程（XP，eXtreme Programming）
#### 2.2.1 XP概述
XP是一种注重软件工程实践的敏捷方法，特别强调代码质量。

#### 2.2.2 XP的价值观
1. **沟通（Communication）**
2. **简单（Simplicity）**
3. **反馈（Feedback）**
4. **勇气（Courage）**
5. **尊重（Respect）**

#### 2.2.3 XP的实践
1. **结对编程（Pair Programming）**
   - 两人共用一台电脑
   - 一人写代码，一人审查
   - 持续代码审查

2. **测试驱动开发（TDD，Test-Driven Development）**
   - 先写测试，再写代码
   - 红-绿-重构循环
   - 确保代码可测试

3. **持续集成（CI，Continuous Integration）**
   - 频繁集成代码
   - 自动化构建和测试
   - 快速发现问题

4. **重构（Refactoring）**
   - 不改变外部行为
   - 改善内部结构
   - 保持代码清洁

5. **简单设计（Simple Design）**
   - 满足当前需求即可
   - 不过度设计
   - YAGNI原则（You Aren't Gonna Need It）

6. **集体代码所有权（Collective Code Ownership）**
   - 任何人可以修改任何代码
   - 共同负责
   - 避免知识孤岛

7. **编码标准（Coding Standards）**
   - 统一的编码规范
   - 提高可读性
   - 减少摩擦

8. **可持续的节奏（Sustainable Pace）**
   - 不加班
   - 保持长期生产力
   - 避免疲劳

9. **现场客户（On-site Customer）**
   - 客户在团队现场
   - 实时解答问题
   - 快速反馈

10. **小版本发布（Small Releases）**
    - 频繁发布
    - 快速获得反馈
    - 降低风险

### 2.3 Kanban（看板）
#### 2.3.1 Kanban概述
Kanban源于丰田生产系统，是一种基于拉动的生产方式。

#### 2.3.2 Kanban的核心实践
1. **可视化工作流（Visualize Workflow）**
   - 看板墙
   - 列表示状态
   - 卡片表示工作项

2. **限制在制品（Limit Work in Progress）**
   - 每列设置WIP限制
   - 防止过载
   - 暴露瓶颈

3. **度量和管理流动（Measure and Manage Flow）**
   - 前置时间
   - 周期时间
   - 吞吐量

4. **明确过程策略（Make Process Policies Explicit）**
   - 完成的定义
   - 工作项的准入准出标准
   - 协作规则

5. **实施反馈循环（Implement Feedback Loops）**
   - 定期回顾
   - 持续改进
   - 团队协作

6. **协作改进（Collaborative Improvement）**
   - 团队参与
   - 实验和学习
   - 持续优化

#### 2.3.3 Kanban板示例
```
待办 | 分析 | 开发 | 测试 | 验收 | 完成
-----|------|------|------|------|------
 [ ] | [ ]  | [ ]  | [ ]  | [ ]  | [ ]
 [ ] | [ ]  | [ ]  |      |      |
 [ ] |      |      |      |      |
     |      |      |      |      |
(WIP:3)(WIP:2)(WIP:3)(WIP:2)
```

### 2.4 Scrum vs Kanban
| 特性 | Scrum | Kanban |
|------|-------|--------|
| 迭代 | 有时间盒的Sprint | 无迭代，持续流动 |
| 角色 | PO、SM、开发团队 | 无特定角色 |
| WIP限制 | 间接限制（通过Sprint） | 直接限制每列WIP |
| 度量 | 速度（Velocity） | 前置时间、周期时间 |
| 实践 | 5个事件 | 6个核心实践 |
| 变更 | Sprint内不变更 | 随时可以变更 |

## 三、敏捷开发的实践
### 3.1 用户故事（User Story）
#### 3.1.1 用户故事格式
```
作为一个<角色>，我想要<功能>，以便<价值>
```

**示例**：
```
作为一个用户，我想要登录系统，以便访问我的个人信息
作为一个管理员，我想要查看用户列表，以便管理用户
```

#### 3.1.2 用户故事的验收标准（Acceptance Criteria）
验收标准定义了用户故事完成的条件：
```
用户故事：登录系统
验收标准：
1. 输入正确的用户名和密码可以成功登录
2. 输入错误的用户名或密码显示错误提示
3. 连续3次登录失败锁定账户10分钟
4. 登录成功后跳转到主页
```

#### 3.1.3 3C原则
1. **卡片（Card）**：简短描述
2. **对话（Conversation）**：详细讨论
3. **确认（Confirmation）**：验收标准

### 3.2 估算
#### 3.2.1 故事点（Story Points）
- 相对估算
- 考虑复杂度、工作量、风险
- 斐波那契数列：1, 2, 3, 5, 8, 13, 21...

#### 3.2.2 规划扑克（Planning Poker）
- 团队成员同时投票
- 讨论差异
- 达成共识

### 3.3 持续集成（CI）
#### 3.3.1 CI的实践
1. **代码仓库**：Git、SVN等
2. **自动化构建**：Maven、Gradle、npm等
3. **自动化测试**：单元测试、集成测试等
4. **CI服务器**：Jenkins、GitLab CI、Travis CI等

#### 3.3.2 CI的好处
- 快速发现问题
- 减少集成问题
- 提高代码质量
- 加速反馈

## 四、敏捷开发的适用场景
### 4.1 适合敏捷的项目
1. **需求不明确或变化频繁**
2. **需要快速交付**
3. **客户参与度高**
4. **团队经验丰富**
5. **创新型项目**

### 4.2 不适合敏捷的项目
1. **需求非常明确且固定**
2. **监管要求严格**
3. **大规模外包项目**
4. **团队分散且难以协作**
5. **关键任务系统**

## 五、敏捷开发的常见误区
1. **敏捷=快速**：敏捷是可持续的开发，不是一味求快
2. **敏捷=没有文档**：敏捷强调可用的文档，不是没有文档
3. **敏捷=没有计划**：敏捷有计划，但计划是灵活的
4. **敏捷=Scrum**：Scrum是敏捷方法之一，不是全部
5. **敏捷=个人英雄**：敏捷强调团队协作，不是个人英雄主义

## 六、敏捷开发的最佳实践
1. **从简单开始**：先采用基本的敏捷实践，再逐步完善
2. **持续改进**：定期回顾，持续优化
3. **团队协作**：培养团队文化，加强协作
4. **客户参与**：保持客户的持续参与
5. **技术卓越**：注重技术实践，保持代码质量
6. **透明沟通**：保持信息透明，及时沟通

# 3.1 软件项目可行性研究内容与步骤笔记

## 一、可行性研究概述
### 1.1 可行性研究的概念
可行性研究是在项目正式启动前，对项目的技术、经济、操作等方面进行分析和评估，以确定项目是否可行。

### 1.2 可行性研究的目的
1. **避免盲目投资**：避免在不可行的项目上浪费资源
2. **降低风险**：识别和评估项目风险
3. **提供决策依据**：为项目决策提供依据
4. **明确方向**：明确项目的目标和方向

### 1.3 可行性研究的重要性
1. **项目成功的基础**：可行性研究是项目成功的基础
2. **资源合理配置**：有助于合理配置资源
3. **提高成功率**：提高项目的成功率
4. **避免损失**：避免不必要的损失

## 二、可行性研究的内容
### 2.1 技术可行性
#### 2.1.1 技术可行性的概念
技术可行性是评估现有技术是否能够实现项目目标，以及技术方案是否可行。

#### 2.1.2 技术可行性分析的内容
1. **技术成熟度**
   - 技术是否成熟
   - 是否有成功案例
   - 技术风险评估

2. **技术能力**
   - 团队技术能力
   - 是否需要外部技术支持
   - 技术培训需求

3. **技术方案**
   - 技术方案的可行性
   - 技术方案的优缺点
   - 技术方案的比较

4. **技术资源**
   - 硬件资源
   - 软件资源
   - 网络资源

#### 2.1.3 技术可行性分析的方法
1. **技术调研**
2. **专家评估**
3. **原型验证**
4. **技术方案比较**

### 2.2 经济可行性
#### 2.2.1 经济可行性的概念
经济可行性是评估项目的经济效益，包括成本估算、收益分析、投资回报等。

#### 2.2.2 成本估算
1. **开发成本**
   - 人力成本
   - 硬件成本
   - 软件成本
   - 培训成本
   - 其他成本

2. **运营成本**
   - 人力成本
   - 维护成本
   - 能源成本
   - 其他运营成本

3. **成本估算方法**
   - 专家估算
   - 类比估算
   - 参数估算
   - 自底向上估算

#### 2.2.3 收益分析
1. **直接收益**
   - 收入增加
   - 成本降低
   - 效率提升

2. **间接收益**
   - 品牌提升
   - 客户满意度提高
   - 竞争力增强

3. **无形收益**
   - 员工满意度
   - 组织能力提升
   - 知识积累

#### 2.2.4 经济评价指标
1. **投资回收期（Payback Period）**
   - 收回投资所需的时间
   - 投资回收期越短越好

2. **净现值（NPV，Net Present Value）**
   ```
   NPV = Σ (CI - CO)t / (1 + i)t
   ```
   - NPV > 0，项目可行
   - NPV越大越好

3. **内部收益率（IRR，Internal Rate of Return）**
   - 使NPV=0的折现率
   - IRR > 基准收益率，项目可行

4. **投资回报率（ROI，Return on Investment）**
   ```
   ROI = (总收益 - 总成本) / 总成本 × 100%
   ```

### 2.3 操作可行性
#### 2.3.1 操作可行性的概念
操作可行性是评估项目在组织内是否能够顺利实施和运行。

   - 人员接受度

3. **流程可行性**
   - 业务流程是否需要调整
   - 新流程的可行性
   - 流程切换的风险

4. **法律可行性**
   - 法律法规要求
   - 知识产权
   - 合同协议
   - 合规性

### 2.4 时间可行性
#### 2.4.1 时间可行性的概念
时间可行性是评估项目是否能够在规定的时间内完成。

#### 2.4.2 时间可行性分析的内容

### 2.5 社会可行性
#### 2.5.1 社会可行性的概念
社会可行性是评估项目对社会的影响以及社会对项目的接受度。

#### 2.5.2 社会可行性分析的内容

# 4.1 软件测试基础笔记

## 一、软件测试概述
### 1.1 软件测试的定义
软件测试是为了发现错误而执行程序的过程。

**Glenford J. Myers的定义**：
1. 测试是为了发现错误而执行程序的过程
2. 好的测试用例是发现至今尚未发现的错误的测试用例
3. 成功的测试是发现了至今尚未发现的错误的测试

### 1.2 软件测试的目的
1. **发现错误**：发现软件中的缺陷
2. **提高质量**：确保软件满足质量要求
3. **降低风险**：减少软件发布后的风险
4. **提供信息**：为决策提供信息

### 1.3 软件测试的原则
1. **完全测试不可能**：不可能测试所有可能的情况
2. **测试显示缺陷的存在**：测试能发现缺陷，但不能证明没有缺陷
3. **尽早测试**：测试应该尽早开始
4. **缺陷群集**：缺陷往往集中在少数模块
5. **杀虫剂悖论**：同样的测试用例会逐渐失去效力
6. **测试依赖上下文**：不同的软件需要不同的测试方法
7. **没有错误的谬论**：即使没有发现缺陷，也不代表软件完美

## 二、软件测试的类型
### 2.1 按测试阶段分类
#### 2.1.1 单元测试（Unit Testing）
**定义**：对软件中的最小可测试单元进行检查和验证。

**目标**：
- 验证每个单元的功能
- 发现单元内部的错误
- 确保单元符合设计

**特点**：
- 测试粒度小
- 可以独立测试
- 通常使用框架（JUnit、pytest等）
- 由开发人员执行

**示例**：
```java
// 被测试的方法
public int add(int a, int b) {
    return a + b;
}

// 单元测试
@Test
public void testAdd() {
    Calculator calc = new Calculator();
    assertEquals(5, calc.add(2, 3));
    assertEquals(0, calc.add(0, 0));
    assertEquals(-1, calc.add(2, -3));
}
```

#### 2.1.2 集成测试（Integration Testing）
**定义**：将多个单元组合在一起进行测试。

**目标**：
- 验证模块间的接口
- 发现集成错误
- 确保模块间正确协作

**集成策略**：
1. **自顶向下集成**
   - 从顶层模块开始
   - 使用桩（Stub）模拟下层模块
   - 优点：早看到系统框架
   - 缺点：需要很多桩

2. **自底向上集成**
   - 从底层模块开始
   - 使用驱动（Driver）模拟上层模块
   - 优点：不需要桩
   - 缺点：最后才看到系统框架

3. **三明治集成**
   - 自顶向下和自底向上结合
   - 优点：效率高
   - 缺点：复杂

#### 2.1.3 系统测试（System Testing）
**定义**：将整个系统作为一个整体进行测试。

**目标**：
- 验证系统是否满足需求
- 发现系统级的错误
- 确保系统符合规格说明

**测试内容**：
- 功能测试
- 性能测试
- 安全测试
- 兼容性测试
- 可靠性测试
- 可用性测试

#### 2.1.4 验收测试（Acceptance Testing）
**定义**：由用户进行的测试，验证系统是否满足业务需求。

**目标**：
- 验证系统是否满足用户需求
- 确认系统可以接受
- 为系统上线做准备

**类型**：
1. **Alpha测试**：在开发环境进行的验收测试
2. **Beta测试**：在用户环境进行的验收测试
3. **UAT（User Acceptance Testing）**：用户验收测试

### 2.2 按测试方法分类
#### 2.2.1 白盒测试（White Box Testing）
**定义**：基于代码内部结构的测试。

**特点**：
- 测试人员可以看到代码
- 测试代码的逻辑路径
- 需要编程知识

**技术**：
- 语句覆盖
- 分支覆盖
- 条件覆盖
- 路径覆盖

**示例**：
```java
public int max(int a, int b) {
    if (a > b) {
        return a;
    } else {
        return b;
    }
}

// 白盒测试用例
// 测试路径1：a > b
max(5, 3)
// 测试路径2：a <= b
max(3, 5)
```

#### 2.2.2 黑盒测试（Black Box Testing）
**定义**：基于功能需求的测试，不考虑内部结构。

**特点**：
- 测试人员看不到代码
- 只关注输入输出
- 不需要编程知识

**技术**：
- 等价类划分
- 边界值分析
- 因果图
- 决策表
- 错误推测

**示例**：
```
功能：登录系统
输入：用户名、密码
输出：登录成功/失败

黑盒测试用例：
1. 正确用户名 + 正确密码 → 成功
2. 正确用户名 + 错误密码 → 失败
3. 错误用户名 + 任意密码 → 失败
4. 空用户名 + 任意密码 → 失败
5. 任意用户名 + 空密码 → 失败
```

#### 2.2.3 灰盒测试（Gray Box Testing）
**定义**：结合白盒和黑盒的测试方法。

**特点**：
- 部分了解内部结构
- 结合两者的优点

### 2.3 其他测试类型
#### 2.3.1 性能测试（Performance Testing）
**目标**：测试系统的性能指标。

**类型**：
1. **负载测试**：在不同负载下测试
2. **压力测试**：在极限情况下测试
3. **稳定性测试**：长时间运行测试
4. **基准测试**：性能基准对比

**指标**：
- 响应时间
- 吞吐量
- 并发用户数
- 资源利用率

#### 2.3.2 安全测试（Security Testing）
**目标**：测试系统的安全性。

**内容**：
- 认证测试
- 授权测试
- 渗透测试
- 漏洞扫描
- 数据加密测试

#### 2.3.3 兼容性测试（Compatibility Testing）
**目标**：测试系统在不同环境下的兼容性。

**内容**：
- 浏览器兼容性
- 操作系统兼容性
- 设备兼容性
- 版本兼容性

#### 2.3.4 回归测试（Regression Testing）
**定义**：在修改代码后重新测试，确保没有引入新错误。

**目标**：
- 确保修改没有破坏现有功能
- 发现回归错误

**方法**：
- 全部重测
- 选择性重测
- 自动化测试

## 三、测试用例设计
### 3.1 测试用例的定义
测试用例是为特定目标而设计的一组输入、执行条件和预期结果。

### 3.2 测试用例的要素
1. **测试用例编号**：唯一标识
2. **测试标题**：简要描述
3. **前置条件**：测试前的条件
4. **测试步骤**：具体的操作步骤
5. **输入数据**：测试输入
6. **预期结果**：预期的输出
7. **实际结果**：实际的输出
8. **测试状态**：通过/失败/阻塞

### 3.3 黑盒测试用例设计方法
#### 3.3.1 等价类划分
**思想**：将输入划分为等价类，从每个类中选取代表性数据。

**步骤**：
1. 划分有效等价类
2. 划分无效等价类
3. 设计测试用例覆盖所有等价类

**示例**：
```
输入：年龄（18-60岁）

有效等价类：
- 18 <= age <= 60

无效等价类：
- age < 18
- age > 60
- age非数字

测试用例：
1. age = 30 → 有效
2. age = 17 → 无效
3. age = 61 → 无效
4. age = abc → 无效
```

#### 3.3.2 边界值分析
**思想**：测试边界值，因为错误往往发生在边界。

**原则**：
- 选取正好等于、刚刚大于、刚刚小于边界的值

**示例**：
```
输入：年龄（18-60岁）

边界值：
- 17（刚刚小于）
- 18（等于）
- 19（刚刚大于）
- 59（刚刚小于）
- 60（等于）
- 61（刚刚大于）
```

#### 3.3.3 决策表
**思想**：分析输入条件的组合和对应的输出。

**组成**：
- 条件桩：输入条件
- 动作桩：输出动作
- 条件项：条件取值
- 动作项：动作取值

#### 3.3.4 错误推测
**思想**：基于经验推测可能的错误。

**方法**：
- 经验判断
- 常见错误列表
- 历史数据

### 3.4 白盒测试用例设计方法
#### 3.4.1 语句覆盖
**目标**：确保每个语句至少执行一次。

**示例**：
```java
if (a > 0) {
    b = 1;  // 语句1
} else {
    b = 2;  // 语句2
}
c = 3;      // 语句3

// 语句覆盖需要：
// a = 1 → 执行语句1、3
// a = -1 → 执行语句2、3
```

#### 3.4.2 分支覆盖（判定覆盖）
**目标**：确保每个判定的真假分支都至少执行一次。

#### 3.4.3 条件覆盖
**目标**：确保每个条件的真假都至少取到一次。

#### 3.4.4 路径覆盖
**目标**：确保程序的每条可能路径都至少执行一次。

# 软件工程基础综合笔记

## 一、软件工程概述
### 1.1 软件与软件工程
- **软件**：计算机程序、数据及其相关文档的完整集合
- **软件的特点**：
  1. 软件是逻辑产品，不是物理产品
  2. 软件没有明显的制造过程
  3. 软件在使用过程中没有磨损、老化问题
  4. 软件的开发和运行受计算机系统的限制
  5. 软件的开发至今尚未完全摆脱手工艺的开发方式
  6. 软件是复杂的
  7. 软件成本相当昂贵
  8. 软件工作涉及很多社会因素

- **软件危机**：
  - 软件开发和维护过程中遇到的一系列严重问题
  - 表现：
    1. 软件开发进度难以预测
    2. 软件开发成本难以控制
    3. 用户对产品功能难以满足
    4. 软件产品质量无法保证
    5. 软件难以维护
    6. 软件通常没有适当的文档资料

- **软件工程**：
  - 是指导计算机软件开发和维护的一门工程学科
  - 是把系统化的、规范化的、可度量的途径应用于软件开发、运行和维护
  - 是研究如何应用上述途径

### 1.2 软件工程的基本原理
1. **用分阶段的生存周期计划严格管理**
2. **坚持进行阶段评审**
3. **实行严格的产品控制**
4. **采用现代程序设计技术**
5. **结果应能清楚地审查**
6. **开发小组的人员应该少而精**
7. **承认不断改进软件工程实践的必要性**

### 1.3 软件工程方法学
1. **传统方法学（生命周期方法学或结构化范型）**：
   - 结构化分析
   - 结构化设计
   - 结构化编程

2. **面向对象方法学**：
   - 对象
   - 类
   - 继承
   - 消息
   - 封装
   - 多态性

### 1.4 软件过程
- **软件过程**：是为了获得软件产品，在软件工具支持下由软件工程师完成的一系列软件工程活动
- **软件过程的基本活动**：
  1. 软件规格说明
  2. 软件开发
  3. 软件确认
  4. 软件演化

## 二、软件生命周期
### 2.1 软件生命周期的阶段
1. **问题定义**：
   - 确定要解决的问题是什么
   - 输出：关于系统规模和目标的报告书

2. **可行性研究**：
   - 确定问题是否值得去解决
   - 输出：系统的高层逻辑模型和可行性研究报告

3. **需求分析**：
   - 确定目标系统必须做什么
   - 输出：需求规格说明书

4. **总体设计（概要设计）**：
   - 确定怎么解决问题
   - 输出：总体设计文档

5. **详细设计**：
   - 具体实现方案
   - 输出：详细设计文档

6. **编码和单元测试**：
   - 编写程序并测试
   - 输出：源程序和单元测试报告

7. **综合测试**：
   - 集成测试、确认测试、系统测试
   - 输出：综合测试报告

8. **软件维护**：
   - 使软件持久地满足用户的需要
   - 输出：维护记录

### 2.2 软件过程模型
1. **瀑布模型**：
   - 阶段间具有顺序性和依赖性
   - 推迟实现的观点
   - 质量保证的观点
   - 优点：
     - 可强迫开发人员采用规范的方法
     - 严格规定了每个阶段必须提交的文档
     - 要求每个阶段的产品都必须经过质量保证小组的仔细验证
   - 缺点：
     - 不灵活
     - 几乎完全依赖于书面规格说明
     - 不能适应用户需求的变化

2. **快速原型模型**：
   - 快速建立一个可以运行的原型
   - 用户试用原型，提出意见
   - 根据意见修改原型
   - 优点：
     - 有助于获取用户需求
     - 减少由于软件需求不明确带来的开发风险
   - 缺点：
     - 原型的快速建立可能导致系统质量下降
     - 原型的迭代可能导致开发时间延长

3. **增量模型**：
   - 分批地逐步向用户提交产品
   - 优点：
     - 可以在开发的早期阶段获得早期的用户反馈
     - 可以降低开发风险
     - 可以较早地向用户提供部分功能
   - 缺点：
     - 增量的划分需要精心设计
     - 需要开放的体系结构

4. **螺旋模型**：
   - 结合了瀑布模型和快速原型模型的优点
   - 加入了风险分析
   - 每个周期包括四个阶段：
     1. 制定计划
     2. 风险分析
     3. 实施工程
     4. 客户评估
   - 优点：
     - 对可选方案和约束条件的强调有利于已有软件的重用
     - 有助于把软件质量作为软件开发的一个重要目标
     - 减少了过多测试或测试不足所带来的风险
     - 在螺旋模型中维护只是模型的另一个周期
   - 缺点：
     - 需要具有相当丰富的风险评估经验和专门知识
     - 如果未及时标记风险，就会造成重大损失

5. **喷泉模型**：
   - 典型的面向对象生命周期模型
   - 各阶段相互重叠
   - 多次反复迭代

6. **Rational统一过程（RUP）**：
   - 用例驱动
   - 以架构为中心
   - 迭代和增量
   - 四个阶段：
     1. 初始阶段
     2. 精化阶段
     3. 构建阶段
     4. 移交阶段

### 2.3 敏捷开发
1. **敏捷宣言**：
   - 个体和交互胜过过程和工具
   - 可以工作的软件胜过面面俱到的文档

## 四、软件设计
### 4.1 软件设计的基本原理
1. **模块化**：
   - 把程序划分成独立命名且可独立访问的模块
   - 每个模块完成一个子功能
   - 把这些模块集成起来构成一个整体，可以完成指定的功能满足用户的需求

2. **抽象**：
   - 抽出事物的本质特性而暂时不考虑它们的细节

3. **逐步求精**：
   - 为了能集中精力解决主要问题而尽量推迟对问题细节的考虑

4. **信息隐藏**：
   - 使得一个模块内包含的信息（过程或数据），对于不需要这些信息的其他模块来说，是不能访问的

5. **模块独立**：
   - 高内聚，低耦合
   - 内聚：
     - 偶然内聚
     - 逻辑内聚
     - 时间内聚
     - 过程内聚
     - 通信内聚
     - 顺序内聚
     - 功能内聚
   - 耦合：
     - 内容耦合
     - 公共耦合
     - 外部耦合
     - 控制耦合
     - 标记耦合
     - 数据耦合

### 4.2 总体设计
1. **设计原理**：
   - 改进软件结构提高模块独立性
   - 模块规模应该适中
   - 深度、宽度、扇出和扇入都应适当
   - 模块的作用域应该在控制域之内
   - 力争降低模块接口的复杂程度
   - 设计单入口单出口的模块
   - 模块功能应该可以预测

2. **启发规则**：
   - 改进软件结构提高模块独立性
   - 模块规模应该适中
   - 深度、宽度、扇出和扇入都应适当
   - 模块的作用域应该在控制域之内
   - 力争降低模块接口的复杂程度
   - 设计单入口单出口的模块
   - 模块功能应该可以预测

3. **图形工具**：
   - 层次图
   - HIPO图
   - 结构图

### 4.3 详细设计
1. **结构程序设计**：
   - 经典的结构程序设计：只允许使用顺序、选择、循环三种基本控制结构
   - 扩展的结构程序设计：还允许使用多分支结构
   - 修正的结构程序设计：还允许使用LEAVE（或BREAK）结构

2. **详细设计的工具**：
   - 程序流程图
   - 盒图（N-S图）
   - PAD图
   - 判定表
   - 判定树
   - 过程设计语言（PDL）

## 五、软件测试
### 5.1 软件测试的目标
1. **测试是为了发现程序中的错误而执行程序的过程**
2. **好的测试方案是极可能发现迄今为止尚未发现的错误的测试方案**
3. **成功的测试是发现了至今为止尚未发现的错误的测试**

### 5.2 软件测试的准则
1. **所有测试都应该能追溯到用户需求**
2. **应该远在测试开始之前就制定出测试计划**
3. **把Pareto原理应用到软件测试中**
4. **应该从"小规模"测试开始，并逐步进行"大规模"测试**
5. **穷举测试是不可能的**
6. **为了达到最佳的测试效果，应该由独立的第三方从事测试工作**

### 5.3 测试方法
1. **白盒测试（结构测试）**：
   - 知道产品内部工作过程
   - 按照程序内部的逻辑测试程序
   - 检验程序中的每条通路是否都能按预定要求正确工作

2. **黑盒测试（功能测试）**：
   - 不考虑程序内部的逻辑结构和内部特性
   - 只依据程序的需求规格说明书
   - 检查程序的功能是否符合它的功能说明

### 5.4 白盒测试技术
1. **逻辑覆盖**：
   - 语句覆盖
   - 判定覆盖
   - 条件覆盖
   - 判定/条件覆盖
   - 条件组合覆盖
   - 点覆盖
   - 边覆盖
   - 路径覆盖

2. **控制结构测试**：
   - 基本路径测试
   - 条件测试
   - 循环测试

### 5.5 黑盒测试技术
1. **等价划分**：
   - 把程序的输入域划分成若干部分
   - 从每个部分中选取少数代表性数据作为测试用例

2. **边界值分析**：
   - 测试输入或输出范围的边界
   - 刚好等于、刚刚大于、刚刚小于边界的值

3. **错误推测**：
   - 基于经验和直觉推测程序中所有可能存在的各种错误
   - 有针对性地设计测试用例

### 5.6 测试策略
1. **单元测试**：
   - 测试模块
   - 重点测试模块的接口、局部数据结构、重要的执行路径、错误处理路径、边界条件

2. **集成测试**：
   - 把模块组装起来进行测试
   - 方法：
     - 非渐增式测试
     - 渐增式测试
       - 自顶向下集成
       - 自底向上集成

3. **确认测试（验收测试）**：
   - 验证软件的功能和性能及其他特性是否与用户的要求一致
   - Alpha测试
   - Beta测试

4. **系统测试**：
   - 把软件系统作为一个整体进行测试
   - 包括：
     - 功能测试
     - 性能测试
     - 压力测试
     - 安全测试

### 5.7 调试
- **调试**：在测试发现错误之后诊断并改正错误的过程
- **调试的途径**：
  1. 蛮干法
  2. 回溯法
  3. 原因排除法

## 六、软件维护
### 6.1 软件维护的定义
- **软件维护**：在软件已经交付使用之后，为了改正错误或满足新的需要而修改软件的过程

### 6.2 软件维护的类型
1. **改正性维护**：
   - 诊断和改正错误
   - 约占总维护工作量的20%

2. **适应性维护**：
   - 为了适应新的软硬件环境变化
   - 约占总维护工作量的25%

3. **完善性维护**：
   - 为了增加新功能，修改已有功能
   - 约占总维护工作量的50%

4. **预防性维护**：
   - 为了提高软件的可维护性、可靠性等
   - 约占总维护工作量的5%

### 6.3 软件的可维护性
- **可维护性**：维护人员理解、改正、改动或改进这个软件的难易程度
- **决定可维护性的因素**：
  1. 可理解性
  2. 可测试性
  3. 可修改性

### 6.4 提高可维护性的方法
1. **建立明确的软件质量目标**
2. **利用先进的软件开发技术和工具**
3. **建立明确的质量保证工作**
4. **选择可维护的程序设计语言**
5. **改进程序的文档**

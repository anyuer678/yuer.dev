# 软件工程基础综合笔记

## 一、软件工程概述
### 1.1 软件与软件工程
- **软件**：计算机程序、数据及其相关文档的完整集合
- **软件的特点**：
  1. 软件是逻辑产品，不是物理产品
  2. 软件没有明显的制造过程
  3. 软件在使用过程中没有磨损、老化问题
  4. 软件的开发和运行受计算机系统的限制
  5. 软件的开发至今尚未完全摆脱手工艺的开发方式
  6. 软件是复杂的
  7. 软件成本相当昂贵
  8. 软件工作涉及很多社会因素

- **软件危机**：
  - 软件开发和维护过程中遇到的一系列严重问题
  - 表现：
    1. 软件开发进度难以预测
    2. 软件开发成本难以控制
    3. 用户对产品功能难以满足
    4. 软件产品质量无法保证
    5. 软件难以维护
    6. 软件通常没有适当的文档资料

- **软件工程**：
  - 是指导计算机软件开发和维护的一门工程学科
  - 是把系统化的、规范化的、可度量的途径应用于软件开发、运行和维护
  - 是研究如何应用上述途径

### 1.2 软件工程的基本原理
1. **用分阶段的生存周期计划严格管理**
2. **坚持进行阶段评审**
3. **实行严格的产品控制**
4. **采用现代程序设计技术**
5. **结果应能清楚地审查**
6. **开发小组的人员应该少而精**
7. **承认不断改进软件工程实践的必要性**

### 1.3 软件工程方法学
1. **传统方法学（生命周期方法学或结构化范型）**：
   - 结构化分析
   - 结构化设计
   - 结构化编程

2. **面向对象方法学**：
   - 对象
   - 类
   - 继承
   - 消息
   - 封装
   - 多态性

### 1.4 软件过程
- **软件过程**：是为了获得软件产品，在软件工具支持下由软件工程师完成的一系列软件工程活动
- **软件过程的基本活动**：
  1. 软件规格说明
  2. 软件开发
  3. 软件确认
  4. 软件演化

## 二、软件生命周期
### 2.1 软件生命周期的阶段
1. **问题定义**：
   - 确定要解决的问题是什么
   - 输出：关于系统规模和目标的报告书

2. **可行性研究**：
   - 确定问题是否值得去解决
   - 输出：系统的高层逻辑模型和可行性研究报告

3. **需求分析**：
   - 确定目标系统必须做什么
   - 输出：需求规格说明书

4. **总体设计（概要设计）**：
   - 确定怎么解决问题
   - 输出：总体设计文档

5. **详细设计**：
   - 具体实现方案
   - 输出：详细设计文档

6. **编码和单元测试**：
   - 编写程序并测试
   - 输出：源程序和单元测试报告

7. **综合测试**：
   - 集成测试、确认测试、系统测试
   - 输出：综合测试报告

8. **软件维护**：
   - 使软件持久地满足用户的需要
   - 输出：维护记录

### 2.2 软件过程模型
1. **瀑布模型**：
   - 阶段间具有顺序性和依赖性
   - 推迟实现的观点
   - 质量保证的观点
   - 优点：
     - 可强迫开发人员采用规范的方法
     - 严格规定了每个阶段必须提交的文档
     - 要求每个阶段的产品都必须经过质量保证小组的仔细验证
   - 缺点：
     - 不灵活
     - 几乎完全依赖于书面规格说明
     - 不能适应用户需求的变化

2. **快速原型模型**：
   - 快速建立一个可以运行的原型
   - 用户试用原型，提出意见
   - 根据意见修改原型
   - 优点：
     - 有助于获取用户需求
     - 减少由于软件需求不明确带来的开发风险
   - 缺点：
     - 原型的快速建立可能导致系统质量下降
     - 原型的迭代可能导致开发时间延长

3. **增量模型**：
   - 分批地逐步向用户提交产品
   - 优点：
     - 可以在开发的早期阶段获得早期的用户反馈
     - 可以降低开发风险
     - 可以较早地向用户提供部分功能
   - 缺点：
     - 增量的划分需要精心设计
     - 需要开放的体系结构

4. **螺旋模型**：
   - 结合了瀑布模型和快速原型模型的优点
   - 加入了风险分析
   - 每个周期包括四个阶段：
     1. 制定计划
     2. 风险分析
     3. 实施工程
     4. 客户评估
   - 优点：
     - 对可选方案和约束条件的强调有利于已有软件的重用
     - 有助于把软件质量作为软件开发的一个重要目标
     - 减少了过多测试或测试不足所带来的风险
     - 在螺旋模型中维护只是模型的另一个周期
   - 缺点：
     - 需要具有相当丰富的风险评估经验和专门知识
     - 如果未及时标记风险，就会造成重大损失

5. **喷泉模型**：
   - 典型的面向对象生命周期模型
   - 各阶段相互重叠
   - 多次反复迭代

6. **Rational统一过程（RUP）**：
   - 用例驱动
   - 以架构为中心
   - 迭代和增量
   - 四个阶段：
     1. 初始阶段
     2. 精化阶段
     3. 构建阶段
     4. 移交阶段

### 2.3 敏捷开发

## 三、需求分析
### 3.1 需求分析的任务
1. **确定对系统的综合要求**：
   - 功能需求
   - 性能需求
   - 可靠性和可用性需求
   - 出错处理需求
   - 接口需求
   - 约束
   - 逆向需求
   - 将来可能提出的要求

2. **分析系统的数据要求**

3. **导出系统的逻辑模型**

4. **修正系统开发计划**

### 3.2 与用户沟通获取需求的方法
1. **访谈**
2. **面向数据流自顶向下求精**
3. **简易的应用规格说明技术**
4. **快速建立软件原型**

### 3.3 结构化分析方法
1. **数据流图（DFD）**：
   - 表示数据和处理过程的关系
   - 基本符号：
     - 正方形（或立方体）：数据的源点/终点
     - 圆角矩形（或圆形）：变换数据的处理
     - 开口矩形（或两条平行横线）：数据存储
     - 箭头：数据流

2. **数据字典**：
   - 描述数据流图中所有元素的定义
   - 内容：
     - 数据流
     - 数据元素
     - 数据存储
     - 处理

3. **判定表**：
   - 描述复杂的条件组合与应做的动作之间的对应关系

4. **判定树**：
   - 判定表的变种，形式更简单

### 3.4 面向对象分析方法
1. **对象模型**：
   - 表示静态的、结构化的系统的"数据"性质
   - 类图

2. **动态模型**：
   - 表示瞬时的、行为化的系统的"控制"性质
   - 状态图

3. **功能模型**：
   - 表示变化的系统的"功能"性质
   - 用例图

## 四、软件设计
### 4.1 软件设计的基本原理
1. **模块化**：
   - 把程序划分成独立命名且可独立访问的模块
   - 每个模块完成一个子功能
   - 把这些模块集成起来构成一个整体，可以完成指定的功能满足用户的需求

2. **抽象**：
   - 抽出事物的本质特性而暂时不考虑它们的细节

3. **逐步求精**：
   - 为了能集中精力解决主要问题而尽量推迟对问题细节的考虑

4. **信息隐藏**：
   - 使得一个模块内包含的信息（过程或数据），对于不需要这些信息的其他模块来说，是不能访问的

5. **模块独立**：
   - 高内聚，低耦合
   - 内聚：
     - 偶然内聚
     - 逻辑内聚
     - 时间内聚
     - 过程内聚
     - 通信内聚
     - 顺序内聚
     - 功能内聚
   - 耦合：
     - 内容耦合
     - 公共耦合
     - 外部耦合
     - 控制耦合
     - 标记耦合
     - 数据耦合

### 4.2 总体设计
1. **设计原理**：
   - 改进软件结构提高模块独立性
   - 模块规模应该适中
   - 深度、宽度、扇出和扇入都应适当
   - 模块的作用域应该在控制域之内
   - 力争降低模块接口的复杂程度
   - 设计单入口单出口的模块
   - 模块功能应该可以预测

2. **启发规则**：
   - 改进软件结构提高模块独立性
   - 模块规模应该适中
   - 深度、宽度、扇出和扇入都应适当
   - 模块的作用域应该在控制域之内
   - 力争降低模块接口的复杂程度
   - 设计单入口单出口的模块
   - 模块功能应该可以预测

3. **图形工具**：
   - 层次图
   - HIPO图
   - 结构图

### 4.3 详细设计
1. **结构程序设计**：
   - 经典的结构程序设计：只允许使用顺序、选择、循环三种基本控制结构
   - 扩展的结构程序设计：还允许使用多分支结构
   - 修正的结构程序设计：还允许使用LEAVE（或BREAK）结构

2. **详细设计的工具**：
   - 程序流程图
   - 盒图（N-S图）
   - PAD图
   - 判定表
   - 判定树
   - 过程设计语言（PDL）

## 五、软件测试
### 5.1 软件测试的目标
1. **测试是为了发现程序中的错误而执行程序的过程**
2. **好的测试方案是极可能发现迄今为止尚未发现的错误的测试方案**
3. **成功的测试是发现了至今为止尚未发现的错误的测试**

### 5.2 软件测试的准则
1. **所有测试都应该能追溯到用户需求**
2. **应该远在测试开始之前就制定出测试计划**
3. **把Pareto原理应用到软件测试中**
4. **应该从"小规模"测试开始，并逐步进行"大规模"测试**
5. **穷举测试是不可能的**
6. **为了达到最佳的测试效果，应该由独立的第三方从事测试工作**

### 5.3 测试方法
1. **白盒测试（结构测试）**：
   - 知道产品内部工作过程
   - 按照程序内部的逻辑测试程序
   - 检验程序中的每条通路是否都能按预定要求正确工作

2. **黑盒测试（功能测试）**：
   - 不考虑程序内部的逻辑结构和内部特性
   - 只依据程序的需求规格说明书
   - 检查程序的功能是否符合它的功能说明

### 5.4 白盒测试技术
1. **逻辑覆盖**：
   - 语句覆盖
   - 判定覆盖
   - 条件覆盖
   - 判定/条件覆盖
   - 条件组合覆盖
   - 点覆盖
   - 边覆盖
   - 路径覆盖

2. **控制结构测试**：
   - 基本路径测试
   - 条件测试
   - 循环测试

### 5.5 黑盒测试技术
1. **等价划分**：
   - 把程序的输入域划分成若干部分
   - 从每个部分中选取少数代表性数据作为测试用例

2. **边界值分析**：
   - 测试输入或输出范围的边界
   - 刚好等于、刚刚大于、刚刚小于边界的值

3. **错误推测**：
   - 基于经验和直觉推测程序中所有可能存在的各种错误
   - 有针对性地设计测试用例

### 5.6 测试策略
1. **单元测试**：
   - 测试模块
   - 重点测试模块的接口、局部数据结构、重要的执行路径、错误处理路径、边界条件

2. **集成测试**：
   - 把模块组装起来进行测试
   - 方法：
     - 非渐增式测试
     - 渐增式测试
       - 自顶向下集成
       - 自底向上集成

3. **确认测试（验收测试）**：
   - 验证软件的功能和性能及其他特性是否与用户的要求一致
   - Alpha测试
   - Beta测试

4. **系统测试**：
   - 把软件系统作为一个整体进行测试
   - 包括：
     - 功能测试
     - 性能测试
     - 压力测试
     - 安全测试

### 5.7 调试
- **调试**：在测试发现错误之后诊断并改正错误的过程
- **调试的途径**：
  1. 蛮干法
  2. 回溯法
  3. 原因排除法

## 六、软件维护
### 6.1 软件维护的定义
- **软件维护**：在软件已经交付使用之后，为了改正错误或满足新的需要而修改软件的过程

### 6.2 软件维护的类型
1. **改正性维护**：
   - 诊断和改正错误
   - 约占总维护工作量的20%

2. **适应性维护**：
   - 为了适应新的软硬件环境变化
   - 约占总维护工作量的25%

3. **完善性维护**：
   - 为了增加新功能，修改已有功能
   - 约占总维护工作量的50%

4. **预防性维护**：
   - 为了提高软件的可维护性、可靠性等
   - 约占总维护工作量的5%

### 6.3 软件的可维护性
- **可维护性**：维护人员理解、改正、改动或改进这个软件的难易程度
- **决定可维护性的因素**：
  1. 可理解性
  2. 可测试性
  3. 可修改性

### 6.4 提高可维护性的方法
1. **建立明确的软件质量目标**
2. **利用先进的软件开发技术和工具**
3. **建立明确的质量保证工作**
4. **选择可维护的程序设计语言**
5. **改进程序的文档**

## 八、总结
软件工程是一门指导软件开发和维护的工程学科，涵盖软件生命周期、软件开发方法、需求分析、软件设计、软件测试、软件维护和软件项目管理等内容。理解和应用软件工程的原理和方法，可以提高软件开发的质量和效率，降低开发成本，延长软件的使用寿命。
